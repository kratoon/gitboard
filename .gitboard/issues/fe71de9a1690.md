## Context

A NAS is usually behind NAT, so a forge's webhooks cannot reach it. The local app detects changes with a filesystem watcher. Users of one instance also need to see each other's changes quickly, and pushes from outside (CLI, other clients) must be noticed.

## Decision

1. **Adaptive polling** is the mechanism. Only clones with an open SSE subscriber are polled. The interval adapts (for example 15 s while active, backing off to about 5 minutes when nothing changes), with jitter, deduplication per remote branch where users share a remote, and a global cap on concurrent git processes (default 2). The numbers are starting points to validate in Phase 0.
2. The probe is a single-ref fetch (not `git ls-remote <ref>`, which sends no ref prefix); a changed tip is fast-forwarded into the clean working tree.
3. **In-process cross-user notification:** a push made through the instance immediately triggers a fetch for other subscribed clones of the same remote branch.
4. **Browsers** are told through SSE (ADR-3f39a2f).
5. **Provider outage or a revoked credential:** reads stay available from the clone and are labelled stale; the affected user's repository shows "remote unreachable" or "reconnect"; other users are unaffected.
6. Webhooks are not part of the MVP (FEAT-04cf779).

## Alternatives considered

- **Webhooks as the primary trigger:** impractical for NAS deployments (ADR-82e7ef1, rejected).
- **Fetching on every request:** multiplies remote traffic by the read rate.
- **Polling every clone on a fixed timer:** wasteful for idle clones on low-power hardware.

## Consequences

- Staleness for outside pushes is bounded by the polling interval.
- The instance has one outbound address; a remote may throttle it (unverified).
- Poll load is `A / I` fetches per second for A subscribed clones at interval I; backoff, deduplication and the concurrency cap exist to keep it low (Phase 0 measures it, FEAT-84505b0).
