## Context

A NAS is typically behind NAT, so provider webhooks usually cannot reach it. The local app detects changes with a filesystem watcher. Users of one instance also need to see each other's changes quickly, and external pushes must be noticed.

## Decision

1. **Polling is the baseline.** Only clones with an open SSE subscriber are polled, with an adaptive interval (for example 15 s while active, backing off to about 5 min when nothing changes), jitter, deduplication per remote branch where users share a remote, and a global cap on concurrent git processes (default 2).
2. The probe is a single-ref fetch (not `ls-remote <ref>`, which sends no ref prefix); a changed tip is fast-forwarded into the clean working tree.
3. **Cross-user notification in-process:** a push made through the instance immediately triggers a fetch for other subscribed clones of the same remote branch.
4. **Real-time to browsers** stays SSE (ADR-3f39a2f); the existing watcher can emit the change event after a fast-forward.
5. **Optional webhook endpoint** with a per-repository secret triggers the same fetch immediately where the instance is reachable. Correctness never depends on it.
6. **Provider outage or revoked credential:** reads stay available from the clone and are labelled stale; the affected user's repository shows "needs credentials" or "remote unreachable"; others are unaffected.

## Alternatives considered

- **Webhooks as the primary trigger (earlier proposal):** impractical for NAS deployments.
- **Fetch on every request:** multiplies remote traffic by read rate.
- **Poll everything on a fixed timer:** wasteful for idle clones and a poor fit for low-power hardware.

## Rationale

Work proportional to *open boards* keeps load low on small hardware, and instance-local notification gives fast cross-user updates without external reachability.

## Consequences

- Staleness for external pushes is bounded by the polling interval (about 15 s active [A]).
- The instance has one outbound IP; remote-side per-IP throttling is possible [A].

## Scalability implications

Poll load is `A / I` fetches/s for A subscribed clones; with 100 active clones at 30 s that is 3.3/s before deduplication and backoff, which is why backoff, dedupe and a concurrency cap are part of the decision (document 07 §7).
