**As a** Gitboard user, **I want** to give issues a due date, see them ordered by it, and have tasks or events that repeat, **so that** I can use Gitboard for day-to-day TODOs and not only for project work.

## Acceptance criteria

### Due date

- [ ] A new optional `due` field on an issue, a calendar date (`YYYY-MM-DD`) and optionally a time. It is stored in the front matter and is absent on issues that have none, so existing issues are unchanged.
- [ ] CLI: `issue create` and `issue update` accept `--due <date>` and `--clear-due`. Besides ISO dates they accept relative forms (`today`, `tomorrow`, `+3d`, `next monday`). `issue show` and `--json` include it.
- [ ] The field is validated and round-trips through `core`, the CLI, the server API and the web UI, with parity between them.

### Due-date view

- [ ] A new view `due` (alongside `kanban` and `backlog`), selectable per repository and per project like the others.
- [ ] It lists open issues ordered by due date, grouped into Overdue, Today, This week, Later and No date. Done columns are hidden unless "Show done" is ticked.
- [ ] Overdue and due-soon issues are highlighted on cards and in the list, and the drawer has a date picker.
- [ ] CLI equivalent, for example `gitboard due [--project --within 7d --overdue --all]`, so agents never need the UI.

### Recurring tasks and events

- [ ] A new optional `repeat` field with a simple rule: daily, weekly (with weekdays), monthly (day of month or nth weekday) and yearly, with an interval (every N) and an optional end date or count.
- [ ] Completing a recurring issue (moving it to a done column) does not just close it. It schedules the next occurrence: `due` advances to the next date after today or the old due date, and the issue returns to its first column. A `lastDone` date or a short history is kept, so the completion is not lost.
- [ ] Events are tasks with a `due` date and optional time/duration that repeat the same way. Whether they need a separate `type` is decided in the design.
- [ ] Missed occurrences do not pile up: if several periods were skipped, only the next future occurrence is created.
- [ ] `repeat` is validated and has a CLI form, for example `--repeat "weekly on mon,thu"` and `--clear-repeat`.

### Quality

- [ ] Date and recurrence logic is pure and unit tested, including time zones, month ends, leap days and DST. Tests also cover CLI, server API and the front matter round trip.
- [ ] README and the agent skill document the new fields, the view and the commands.

## Out of scope

- Reminders, notifications and calendar sync (iCal, Google Calendar). Gitboard is local-first with no background service. Exporting an `.ics` file could be a later story.
- A full RFC 5545 recurrence engine. Start with the simple rules above.

## Open points

- Where does the recurrence advance happen? Gitboard has no daemon, so it has to happen when the issue is moved to a done column, not on a timer. Settle this in an ADR, together with the front matter shape of `due` and `repeat`.
- Should recurrence mutate the one issue (simple, loses history in git only) or create a new issue per occurrence (clear history, more files)? Recommendation: mutate the one issue and keep `lastDone`.
- Do dates carry a time zone, or are they floating local dates? Recommendation: floating local dates, with an optional local time.
- Overlap with the story "Track GitHub PRs, commits and other links on issues" (FEAT-e66cc63): none, but both add front matter fields, so agree on a consistent naming style.
