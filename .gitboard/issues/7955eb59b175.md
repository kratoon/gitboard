## Context

The local product stores issues as Markdown in Git (ADR-30abf7d) but never writes to Git itself (ADR-7027c6a). A hosted, multi-user server invites designs where a server-side store becomes the working truth and Git an export. The project owner set the principle that Git stays the source of truth, that changes pushed from anywhere remain compatible, and that external changes are never silently overwritten.

## Decision

1. All authoritative issue and project data lives in the Git repository (`.gitboard/`), in the existing format. The hosted app adds no authoritative store.
2. Derived data (caches, parsed snapshots, indexes) is allowed only if it can be rebuilt from Git alone, and is never read to answer a question that must be correct (writes, conflict checks, authorisation).
3. A write is reported successful only after the Git remote has accepted the push that contains it. There is no write-behind queue and no acknowledged local-only commit.
4. Every write is a fast-forward of the remote branch. A commit that is not a descendant of the remote tip is never force-pushed: the operation is re-run on the new tip or fails with a conflict error.
5. The hosted app reads and writes exactly the format the CLI does and tolerates everything the CLI tolerates (unknown keys, CRLF, a BOM, stray files reported by `validate`). Hand edits and pushes from any Git client are first-class.
6. The hosted write path extends ADR-7027c6a ("never commits or pushes") for the hosted server only. The local CLI and `gitboard start` keep that rule; an opt-in `gitboard sync` is planned (FEAT-54f054d).

## Alternatives considered

- **A database as the working store with Git synchronisation:** two representations of every issue, a synchronisation protocol with its own failure modes, and Git demoted to an export. Rejected.
- **A provider API as the store:** quotas, provider lock-in, listing limits. Rejected (ADR-b33c5a6).
- **Write-behind to Git for lower latency:** acknowledges before durability. Rejected.

## Consequences

- Write latency is at least one push round trip.
- Ordering per branch is the remote's ref update.
- State that is not issue data (notifications, assignments to people outside the repository) cannot live in issue files; it needs the profile, Git, or an explicitly non-authoritative store.
