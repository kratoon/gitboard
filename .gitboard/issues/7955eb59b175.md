## Context

The local product stores issues as Markdown in Git (ADR-30abf7d) but never writes to Git itself: users commit and merge (ADR-7027c6a). A
hosted, multi-user product tempts designs where a server-side store becomes the working truth and Git an export. The project's
non-negotiable principle is that Git stays the source of truth, that local pushes remain compatible, and that external changes are
never silently overwritten.

## Decision

1. **All authoritative issue and project data lives in the Git repository** (`.gitboard/`), in the existing format. Hosted GitBoard adds no authoritative store.
2. **Derived data** (caches, parsed snapshots, indexes, search, aggregates) is allowed only if it can be rebuilt from Git alone and is never read to answer a question that must be correct (writes, conflict checks, authorisation).
3. **Durability definition.** A write is reported successful only after the Git remote accepted the push that contains it. There is no write-behind queue, no local-only commit that is acknowledged, no "eventually persisted" state.
4. **No silent overwrite.** Every write is a fast-forward of the remote branch tip. A commit that is not a descendant of the current remote tip is never force-pushed; the operation is re-run against the new tip or fails with a conflict error.
5. **Compatibility.** The hosted service reads and writes exactly the format the CLI reads and writes, and tolerates anything the CLI tolerates (unknown keys, CRLF, BOM, stray files reported by `validate`). Hand edits and local pushes through any Git client are first-class.
6. The hosted write path is an **extension** of ADR-7027c6a ("never commits/pushes"), valid for hosted mode only; the local CLI keeps the rule. On acceptance, ADR-7027c6a gets an amendment note.

## Alternatives considered

- **Database as the working store with Git sync** (Option C): two representations of every issue, a synchronisation protocol with its own failure modes, and Git demoted to an export. Rejected as primary architecture.
- **Provider API as the store** (Option A): see ADR-b33c5a6.
- **Write-behind to Git for lower latency:** acknowledges before durability; violates (3).

## Rationale

The product's value proposition is that issues live with the code and survive without the tool. A single source of truth removes
reconciliation as a class of bug and makes the hosted and local products interchangeable views of the same repository.

## Consequences

- Write latency is bounded below by a Git push round trip (see scalability analysis for estimates).
- Per-branch ordering is the provider's ref update; throughput per branch is limited accordingly (ADR-db6547a).
- Features that need non-Git state (notifications, assignments to non-members, per-user preferences) cannot be stored in issue data; they need a clearly labelled, non-authoritative store (see ADR-099d4df).

## Scalability implications

Git is a bottleneck per repository branch, not globally: repositories are independent, so aggregate throughput scales with the number of repositories and nodes. The cost is that a single hot branch has a hard ceiling (analysed in FEAT-84505b0 (capacity model)).

## Amendment 2026-11-21 (self-hosted direction)

Still applies unchanged. Under the self-hosted design the remote is any Git remote, "accepted by the remote" means a successful push with the user's own credential, and the CLI and hosted server remain format-compatible. See ADR-819be48 and ADR-0aa6b23.
