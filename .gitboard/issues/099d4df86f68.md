## Context

Multi-user web applications default to a database. Here a database holding issues would become a second source of truth. Some non-issue state exists (accounts, credentials, profiles), and later features (cross-repository search) may justify a derived index.

## Decision

1. Issue and project data is never stored in a database as the authoritative copy, and no read that must be correct (writes, conflict checks, authorisation) consults a derived store.
2. The MVP has no database at all: accounts and identities are in `users.json`, OAuth tokens in encrypted files, profiles in files, all on the instance's data volume (ADR-87400e0, ADR-7d58e8b).
3. A derived, rebuildable index (search, cross-repository aggregation) may be added only if all of these hold: a measured need that clone-based reads cannot meet; it is built solely from Git and can be dropped and rebuilt without loss; every answer that drives a write is re-validated against Git; its freshness is shown to users; isolation between users is enforced and revocation purges it.
4. A database for non-issue metadata becomes a candidate only past about 200 users or for needs files cannot meet (audit retention, quotas at scale), and needs its own ADR.

## Alternatives considered

- **Database-centric application with Git synchronisation:** two representations of state, synchronisation conflicts, Git as export. Rejected.
- **A database from day one "for sessions and metadata":** an extra failure domain and a temptation to store issue data, before any requirement needs it. Rejected.
- **Embedded SQLite as a derived index now:** fits the criteria above but is not needed yet; admissible later under decision 3.

## Consequences

- Features that need non-Git per-user state must use the profile or an explicit, labelled store.
- Cross-repository views are expensive until an index exists (FEAT-8a3d1a5).
- No database means no database bottleneck or connection limits.
