- **Date:** 2026-11-21
- **Basis:** Rejection of Option C is a stated owner decision; admission criteria below are proposed.
- **Related:** FEAT-8c2e32c, ADR-7955eb5, ADR-dc3a07e, ADR-79c71bc, ADR-30abf7d

## Context

Multi-user web applications default to a relational database. Here, a database holding issues would become a second source of truth.
Some non-issue state still exists (sessions, credentials, audit, quotas), and later features (cross-repo search) may justify derived indexes.

## Decision

1. **Issue and project data is never stored in a database as the authoritative copy**, and no read that must be correct (writes, conflict checks, authorisation) consults a derived store.
2. **Launch without a database** (Phases 2-3): encrypted session cookies, tenancy derived from the provider (installations and repository lists cached in memory), idempotent webhook handling, idempotency via commit trailers, in-memory queues and leases.
3. **Metadata store admission.** A small relational or key-value store may be introduced for *non-issue metadata only* (refresh tokens if cookies prove unsuitable, audit log, per-tenant quotas and billing, installation registry) when a requirement cannot be met statelessly. It needs its own ADR.
4. **Derived index admission criteria.** A rebuildable index (search, cross-repository aggregation, analytics) may be added only if **all** hold: (a) a product requirement that per-repo snapshots cannot meet within latency/cost targets (measured); (b) it is built solely from Git snapshots and can be dropped and rebuilt without loss; (c) every answer that drives a write is re-validated against Git; (d) its freshness is exposed to users; (e) tenant isolation is enforced in the index, and revocation purges it.

## Alternatives considered

- **Database-centric with Git sync (Option C):** rejected as primary; synchronisation conflict handling, split-brain and "Git as export" risks outweigh query convenience.
- **Database from day one "for sessions and metadata":** invites scope creep and an extra failure domain before any requirement needs it.
- **Embedded SQLite per node as a derived index:** attractive for per-node search because it is local and rebuildable; fits criteria (b)-(e); not needed until (a).

## Rationale

Every state we do not store cannot diverge. The snapshot cache already answers per-repository queries from memory; the first feature that needs more is cross-repository search, and even then the answer is a rebuildable index, not a store.

## Consequences

- Features requiring non-Git per-user state (notifications, saved filters across devices) need the metadata store or must live in Git; each such feature should state which.
- Global rate limiting, cross-node dedupe and long-retention audit are limited until a store exists.
- Cross-repository views are expensive until an index exists (FEAT-61ef959).

## Scalability implications

No database means no database bottleneck and no connection-pool limits, at the price of per-node memory for snapshots and no cheap global queries. A derived index per node (sharded like repositories) scales with the same key.

## Open questions

- ADR-099d4df whether a metadata store is needed at launch; FEAT-61ef959 when search/aggregation justify an index.


## Amendment 2026-11-21 (self-hosted direction)

Still applies. Accounts, sessions secret and encrypted credentials are kept in plain files in the instance data directory (ADR-87400e0); that is non-issue metadata and does not need a database. Per-user settings go to the versioned profile (ADR-7d58e8b). A database or SQLite becomes a candidate only past ~200 users or for a derived search index under the admission criteria above.
