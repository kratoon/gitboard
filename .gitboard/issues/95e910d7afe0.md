- **Date:** 2026-11-14
- **Related:** ADR-9b13ab6, ADR-30abf7d, ADR-c680df6, FEAT-b5fe9d6
\1- **Amended 2026-11-14 (ordering):** ranked and unranked cards now share one sort key, so a move never writes the neighbouring cards (before, unranked neighbours were given ranks first, which rewrote many files). Only the moved card's file changes.

## Context

Users want to hand-order cards within a column. Order must be stored in the issue files, since there is no
database, and it must keep the flat layout (ADR-30abf7d) and merge well across branches.

## Decision

- Add an optional `rank` string to issue frontmatter. It is a fractional index (lexicographically
  sortable), for example `a0`, `a1`, `a0V`.
- Within a column (the issues of one project with one status), cards are ordered by **sort key**, ties broken by ID.
  A card's sort key is its `rank`; if it has none, it is a key derived from its priority (highest first), then
  `createdAt`, then id. The derived key is itself a valid rank, so ranked and unranked cards share one scale. Ranks
  written by earlier versions (`a0`, `a1`, ...) sort before every derived key.
- Reordering writes only the moved issue's file. Its new `rank` is chosen between its two neighbours' sort keys,
  whether or not they have a rank, so no other file is ever written. `top` picks a key below the whole derived
  range, so it stays on top when later cards arrive.
- Core owns rank computation. The only case that writes other cards is a column whose neighbours cannot be
  separated (equal or inverted ranks left by a merge, or a hand-edited rank that is not a valid key): the column is
  then re-ranked once.
- Operation (registered per ADR-9b13ab6): `moveIssue(id, { status?, before?, after?, position? })`. CLI:
  `gitboard issue move <id> <status> [--before <id> | --after <id> | --top | --bottom]`. Without a position the issue is
  not ranked at all (see the amendment above). The UI drag-and-drop calls the same operation.
- Moving a card to the position it already occupies writes nothing. Ordering is bookkeeping: a change to `rank`
  alone never stamps `updatedAt`, so reordering does not mark issues as edited (amended 2026-11-14).
- `validate` does not require ranks. Duplicate ranks are legal and resolved by the tie-break.
- Created issues get no `rank`: they sort by priority and date, so they land after cards of the same priority that
  were created earlier.

## Alternatives considered

- **No stored order:** simplest, but no hand ordering.
- **Board-level `order.json`:** one hot file that conflicts on nearly every merge.
- **Integer positions:** moving one card renumbers many files.

## Consequences

- One extra optional field, backward compatible with existing files.
- Merge conflicts occur only if the same card is reordered on two branches. Two different cards that end up
  with the same rank are handled by the tie-break.
- Agents can order issues through the CLI, so ordering stays CLI-first.
- A card you placed keeps its position among the cards that were around it when you placed it. Cards that arrive
  later sort by priority and creation time, so a new urgent card appears above manually ordered medium cards, but
  never above a card pinned with `top`.
