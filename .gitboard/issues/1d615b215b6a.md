- **What:** when the repository config on the checked-out branch has `branch: X` and X is not the current branch, the local CLI and app resolve the board to a worktree of X (created on first use, kept under `.git/`) instead of reading or writing `.gitboard/` on the current branch. This lets agents working on feature branches update the shared board when it lives on a dedicated branch.
- **Why deferred:** hosted MVP only reads and writes the resolved board branch. For repositories where agents change issues together with code, the board stays on the default branch (hosted status then lags until the PR merges, which is accepted). Until this is built, a local user with a dedicated board branch registers a worktree of that branch as the repository (`gitboard -r <path>` already works) and the Phase 1 guard makes the CLI refuse writes on a branch whose config points elsewhere (reads print a hint).
- **Why it matters:** without it, an agent running the CLI from a code clone with a dedicated board branch would write issue changes onto the code branch, where the hosted app ignores them.
- **Related:** FEAT-8c2e32c, FEAT-0a956bc, FEAT-cd25599
- **Decision folded in (owner, 2026-11-21):** which branch the hosted "enable Gitboard" dialog preselects (the default branch, or a dedicated branch named `gitboard`) is decided here, not now. Trade-offs recorded so far: a dedicated branch avoids CI noise and protection problems and keeps clones tiny, but issue changes no longer travel with code, local agents need this story's worktree redirect, and teammates need the `branch` pointer on the default branch (blocked when it is protected) unless a conventional branch name is auto-discovered (FEAT-eee6af6). Current recommendation: preselect the default branch, show both choices with these trade-offs, and offer a dedicated `gitboard` branch when the push to the default branch is rejected.
