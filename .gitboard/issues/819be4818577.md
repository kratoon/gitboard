## Context

The intended deployment is self-hosting: anyone runs their own instance (the owner's NAS first) for a handful to a few dozen users, with clones and working trees acceptable. The existing core, CLI and web UI must keep working unchanged, and the local app must remain.

## Decision

1. Hosted Gitboard is a **self-hostable server**, started with a new command `gitboard serve`, shipped in the same npm package and as a container image. `gitboard start` remains the loopback, single-user local app.
2. The design is provider-independent: the Git data path is plain Git over HTTPS and uses no forge API. The MVP supports GitHub; other forges arrive as adapters (FEAT-caff4fa).
3. **Scale model: shared-nothing instances.** One process, one data directory, in-process locks. Capacity is vertical and bounded (tens of users; roughly 200 on a low-end NAS). There is no sharding or coordination service; more capacity means another independent instance.
4. The existing filesystem core, CLI and web UI are reused unchanged; the server is a new adapter plus a Git sync layer (ADR-0aa6b23).
5. **Docker is the only supported deployment**, because a Git or parser vulnerability must be confined to the data volume. Requirements, risks and quotas are in ADR-87400e0. Running `gitboard serve` on a network-reachable bind outside a container is unsupported: it warns loudly at startup and requires an explicit flag acknowledging that. A loopback bind outside a container needs neither. The image sets a marker the server uses to recognise a container.
6. **Image:** `linux/amd64` and `linux/arm64` (no 32-bit ARM); Node 22 (the npm package keeps `engines: >=20` for local use); a current patched Git configured by Gitboard on every call, not by a system gitconfig, with a startup check that refuses to run below the minimum version (the oldest that passes the Phase 0 spikes; the sparse index needs 2.37 or newer); no SSH client in the MVP image (SSH is deferred); non-root user, read-only root filesystem, one `/data` volume, secrets as files, the existing `/api/health` as healthcheck. Rebuilt weekly and on Git security releases; published to GitHub Container Registry with exact-version and `latest` tags, built with buildx in CI on release, sharing the npm package's version.
7. The server runs on Linux only; the CLI and `gitboard start` stay cross-platform (ADR-9b39f45).

## Alternatives considered

- **An operator-hosted service on a GitHub App for many tenants:** heavy infrastructure, provider quotas, multi-tenant security. Rejected (ADR-375920a, ADR-79c71bc, ADR-b33c5a6, ADR-0495ea1, ADR-6f6fd0c, ADR-db6547a, ADR-82e7ef1, ADR-9eb2543).
- **Only the local app, one per person:** works for one user; gives no shared access or per-user login on one machine.
- **A server that stores issues itself in a database:** rejected (ADR-099d4df).
- **Hard refusal outside a container:** rules out running on a bare server. Rejected.
- **Supporting bare-host deployment with documented hardening:** a larger support surface. Rejected for now.

## Consequences

- Operators are responsible for TLS (reverse proxy), backups of the data directory, and updating the image to receive Git patches.
- When the remote is GitHub, its recommendations (about 6 pushes and 15 read operations per second per repository) still apply.
- A second instance, not a bigger one, is the answer to growth past a low-end NAS.
