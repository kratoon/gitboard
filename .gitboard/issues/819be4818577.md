## Context

The first hosted analysis assumed an operator-run service for many tenants on GitHub. The intended deployment is different: anyone runs their own instance (the owner's NAS first) for a handful to a few dozen users, against any Git remote (GitHub, GitLab, Gitea, plain SSH), with clones and working trees acceptable.

## Decision

1. Hosted Gitboard is a **self-hostable server**, started with a new command `gitboard serve`, shipped in the same npm package and as a container image. `gitboard start` remains the loopback, single-user local app.
2. It works with **any Git remote** over SSH or HTTPS. No provider API is on any data or authorisation path; remote authorisation is whatever the user's own credential is allowed to do.
3. **Scale model: shared-nothing instances.** One process, one data directory, in-process locks; capacity is vertical and bounded (tens of users). There is no horizontal scaling design, no sharding and no coordination service. More capacity means another independent instance.
4. The existing filesystem core, CLI and web UI are reused unchanged; the server is a new adapter plus a Git sync layer (ADR-0aa6b23).
5. Provider-specific integrations (webhooks, forge login) are optional extras, never required.

## Alternatives considered

- **Operator-hosted SaaS on a GitHub App:** the earlier analysis (documents 02-04); heavy infrastructure, quotas, multi-tenant security. Not the intended product. Kept as archived analysis.
- **Only the local app, with each person running it:** works today for single users; does not give shared access or per-user login on one box.
- **A server that stores issues itself (database):** rejected (ADR-099d4df).

## Rationale

The requirement is to host on a NAS and let others host it. That favours minimal dependencies, a small footprint and reuse of the working local core over a scalable multi-tenant platform.

## Consequences

- Operators are responsible for TLS (reverse proxy), backups of the data directory, and keeping Git patched.
- The scalability work shifts from throughput at scale to a predictable small-footprint resource model (see Resource model below).
- GitHub-specific limits still matter when the remote is GitHub (about 6 pushes/min per repository recommended).

## Scalability implications

Bounded by one Node process and NAS hardware; target tens of users, hundreds of clones. The documented ceiling is ~200 users on a low-end NAS, beyond which a second instance is recommended.

## Open questions

- FEAT-f5a9856 packaging; FEAT-926a35e isolation promise; FEAT-94dfdce shared team credential.

## Components

- **`gitboard serve`** (new command; `start` stays loopback-only and single-user): a single Node process with one data directory. It refuses a non-loopback bind without authentication.
- **Accounts and sessions, credential store:** see the accounts ADR.
- **HTTP adapter:** the existing operation registry, with a per-request user context that resolves the user's repositories and clone paths.
- **Sync manager:** owns every Git network action and each clone's working tree: per-clone read/write lock, fetch, fast-forward, commit, push, retry, adaptive polling, cross-user notification, SSE.
- **Managed clones:** one per (user, repository), see the clones ADR. **Profile:** see the profile ADR.
- **Core, CLI, web:** unchanged business logic and formats; the CLI and `start` keep working against the same repository format.

## Changes to the existing code base

- `core/storage/userdirs.ts`, `registry-file.ts`, `repos/registry.ts`: the registry and the managed-clone directory come from process-global `userDirs()`; introduce an explicit resolver context (small; ADR-7027c6a's third constraint anticipated this seam).
- `core/storage/git.ts` `runGit`: already takes `extraEnv`, which is where per-user `GIT_SSH_COMMAND` or askpass go; add hardened defaults (small).
- `core/repos/remote.ts`: SSH-only today; add HTTPS with an allowed-hosts list and private-address blocking, in hosted mode only (small).
- `core/repos/registry.ts` `registerRepo`: hosted clone options (treeless, sparse index of `.gitboard/`); local-path registration disabled in hosted mode (small).
- New `core/git/sync.ts` using only `runGit` (medium); also enables an opt-in `gitboard sync` for CLI users, as ADR-7027c6a anticipated.
- `src/server/security.ts`: configurable public URL for Host/Origin checks plus CSRF for cookie auth (small). `src/server/index.ts`: second server mode with auth middleware and per-user resolution; `watch.ts` is reused (medium). `src/web`: login screen; preferences through `GitboardClient` instead of `localStorage` (small).
- Not needed under this design: a storage interface, a plumbing commit builder, bare caches, sharding.

## Resource model (self-hosted, all figures are assumptions until measured, see FEAT-84505b0)

- **Disk:** users x repositories x clone size; a clone is about 0.2 MB plus the tip's trees (0.1-5 MB; 5-50 MB at 10^5-10^6 files) plus issues at 1.5 KB x 2. Example: 50 x 50 x 3 MB is about 7.5 GB.
- **Memory:** Node baseline 100-200 MB, transient parse about 5 MB per 1,000 issues, git processes 20-60 MB each capped at 2-4. Fits 1-2 GB.
- **Reads:** the existing `snapshot()` reads and parses every issue file, about 50-150 ms per 1,000 issues on NAS-class CPU; 20 active users at 0.2 requests/s each is about 0.2-0.6 core. Above about 30 active users on large boards the tree-keyed snapshot cache becomes worthwhile.
- **Polling:** `A / I` fetches per second for A subscribed clones at interval I; 100 clones at 30 s is 3.3/s (0.3-1 core), hence idle backoff to about 5 minutes, deduplication per remote branch and a concurrency cap of 2.
- **Writes:** one push round trip plus commit, 0.5-2 s, serial per clone. Contention comes only from external pushers because an in-process mutex serialises this instance's users; naive retry costs W(W+1)/2 pushes for W simultaneous writers.
- **Provider recommendations for GitHub remotes:** about 6 pushes and 15 read operations per second per repository. The instance has one outbound IP, so per-IP throttling by a remote is possible (unverified).
- **Bound:** one Node event loop (shared-nothing second instances are separate deployments), NAS CPU for git and the O(issues) read, and the remote's own limits.

## Scenarios

1. Solo NAS, 1 user, 10 repositories: trivial.
2. 10 users x 10 repositories: about 300 MB, under 1 request/s; baseline design is sufficient.
3. 50 users x 50 repositories: about 7.5 GB; 100 active clones need adaptive polling, deduplication, possibly the snapshot cache, and quotas.
4. 200 users: edge of a low-end NAS; recommend a second independent instance per team (or snapshot cache, shared object store, a different account store).
5. One hot repository, 20 concurrent writers: push mutex plus bounded jittered retry, about 10-40 s worst case for the last writer.
6. Burst of automation writes: per-clone queue and a global git concurrency cap give back-pressure (429/503); there is no write-behind.
7. Huge repository with a tiny `.gitboard/`: clone cost is dominated by trees (GitHub's study of a 4 GB repository measured 1.2-5 minutes for shallow, full and blobless clones); use a shallow clone for such repositories or a dedicated board branch; GitHub advises against repeated shallow fetches.
8. NAS reboot or remote outage: startup resets clones to the remote; reads come from the clone labelled stale; writes fail fast; nothing acknowledged is lost.

## Decision update 2026-11-21 (owner): Docker only

The supported way to run `gitboard serve` is a container (details, requirements and quotas in the accounts ADR). Running it directly on a host is possible but unsupported, and the operator documentation, written when the feature ships, must say so and open with the risks, requirements and quotas.
