- **Question:** Does each user get an independent managed clone of each repository, or one shared bare object store per remote with a `git worktree` per user?
- **Why it matters:** Disk and fetch duplication versus credential isolation and locking complexity. With a shared store, objects fetched with user A's credential become readable through user B's worktree unless access is proven first.
- **Options:** (1) Independent clone per (user, repository), blobless with cone sparse checkout of `.gitboard/`. (2) Shared bare store per remote plus per-user worktrees (a worktree cannot check out a branch another worktree has; use a per-user local branch). (3) One shared clone with a service credential (loses per-user identity).
- **Recommendation:** Option 1 first. Typical clones are a few MB, so 50 users x 50 repositories is about 7.5 GB (assumption). Move to option 2 only if the Phase 0 spikes show duplication hurts, with a per-user access proof (authenticated fetch or ls-remote) before any worktree is created or updated. Temporary worktrees remain the tool for a future PR mode.
- **Related:** FEAT-8c2e32c, ADR-0aa6b23, ADR-819be48
- **Decision / date:** 2026-11-21. Option 1: an independent managed clone per (user, repository), blobless with a cone sparse checkout of `.gitboard/`. Option 2 (shared object store with per-user worktrees) is the planned upgrade, to be revisited only if the Phase 0 measurements show disk or fetch duplication matters. It is reversible: clones hold nothing that is not on the remote, so a switch means recreating them. Constraints that keep the switch cheap: (1) all clone creation, sync and path lookup in one module; (2) clone paths never stored, computed from user and canonical remote URL; (3) a canonical-URL function from the start; (4) Git identity and credentials passed per call (environment or `-c`), never written to a clone's `.git/config`; (5) nothing assumes `.git` is a directory. If option 2 is built later it needs the access-proof rules: a worktree only moves to a commit that the user's own credential just proved it can see, per-user refs in the store, no credentials in the store's config, revocation deletes the user's worktree, one choke point with cross-user leak tests. Recorded in ADR-0aa6b23.
