- **Goal:** replace the assumptions behind the capacity model with measurements, and settle the blocking questions (clone layout, credentials, settings split, Gitboard branch).
- **Spikes (throwaway, no product code):**
  1. Per-user SSH key and token handling, `known_hosts`, on the target NAS operating system.
  2. Treeless (`tree:0`) clone with a cone sparse checkout of `.gitboard/` in sparse-index mode, against real GitHub and Gitea remotes: time, size and update cost on typical and very large repositories; compare with the blobless fallback; check that a single-ref fetch plus reset works, and, only if needed, the shared-object-store option.
  3. Poll cost on NAS CPU: single-ref fetch cost, deduplication per remote, idle backoff.
  4. Push races with 5-20 writers against GitHub and a Gitea: attempts per success, error texts, protected-branch and signed-commit behaviour.
  5. Idle and peak memory and CPU of Node plus git on the target hardware.
- **Assumptions to replace (all unmeasured):** 1.5 KB per issue file; read cost 50-150 ms per 1,000 issues on NAS-class CPU; clone size 1-6 MB for typical repositories; push round trip 0.5-2 s; 2-4 low-power cores, 2-8 GB RAM; poll load `A / I` fetches per second for A subscribed clones at interval I (100 clones at 30 s is 3.3/s before deduplication and backoff).
- **Capacity model (formulas to validate):** disk is users x repositories x clone size (50 x 50 x 3 MB is about 7.5 GB); naive parallel push retries cost W(W+1)/2 attempts for W simultaneous writers (5 writers: 15, 100 writers: 5,050); a write's history cost is roughly 0.4-1 KB of pack per commit. Practical ceiling for one low-end NAS is estimated at about 200 users; beyond that, run a second independent instance.
- **Verified facts to build on:**
  - Measured locally (git 2.54, synthetic repository of 3,200 code files and 200 issues, over `file://`): treeless plus cone sparse index fetched 200 blobs, 41 commits and 304 trees (versus 3,280 blobs and 504 trees for a full clone); reading one path fetched the whole tip tree set; each upstream commit then added about 5-7 trees and the changed blobs; commits in the sparse-index clone touched only `.gitboard`.
  - Measured locally with git 2.54: a blobless clone has all commits and all historical trees and no blobs; lazy fetching runs one fetch per missing object (bulk prefetch by object id runs one); sparse checkout affects only the working tree, and without a filter a sparse clone still downloads every object; pushing a commit on top of a shallow boundary to a full remote works; `ls-remote <ref>` sends no ref prefix while a single-ref `fetch` does; a flat tree costs 43 bytes per entry (430,000 bytes at 10k issues, 4,300,000 at 100k) and a one-file change is a thin pack of 272-392 bytes.
  - From GitHub's documentation (read from the `github/docs` and `github/rest-api-description` sources, since docs.github.com was unreachable from the research sandbox): recommended maximums of 15 Git read operations per second and 6 pushes per minute per repository, 3,000 entries per directory, 5-10 GB repository size; push size enforced at 2 GB, object at 100 MB; REST 5,000 requests per hour per user and secondary limits (80 content-creating requests per minute); repeated shallow fetches are described as the worst option for the server; blobless is the recommended partial clone; webhooks time out at 10 s, are not redelivered automatically and are kept 3 days.
  - Git security: checkout-time and submodule vulnerabilities dominate recent advisories (GitHub security blog posts of May 2024, Jan 2025, Jul 2025, Nov 2026); advisory identifiers were not cross-checked against git-scm release notes.
- **Validation milestone:** written results recorded in this issue, the capacity model updated, and the blocking questions decided.

- **Resource model and scenarios (from the self-hosted ADR, assumptions to validate):**

**Resource model (all figures are assumptions until measured):**

- **Disk:** users x repositories x clone size; a clone is about 0.2 MB plus the tip's trees (0.1-5 MB; 5-50 MB at 10^5-10^6 files) plus issues at 1.5 KB x 2. Example: 50 x 50 x 3 MB is about 7.5 GB.
- **Memory:** Node baseline 100-200 MB, transient parse about 5 MB per 1,000 issues, git processes 20-60 MB each capped at 2-4. Fits 1-2 GB.
- **Reads:** the existing `snapshot()` reads and parses every issue file, about 50-150 ms per 1,000 issues on NAS-class CPU; 20 active users at 0.2 requests/s each is about 0.2-0.6 core. Above about 30 active users on large boards the tree-keyed snapshot cache becomes worthwhile.
- **Polling:** `A / I` fetches per second for A subscribed clones at interval I; 100 clones at 30 s is 3.3/s (0.3-1 core), hence idle backoff to about 5 minutes, deduplication per remote branch and a concurrency cap of 2.
- **Writes:** one push round trip plus commit, 0.5-2 s, serial per clone. Contention comes only from external pushers because an in-process mutex serialises this instance's users; naive retry costs W(W+1)/2 pushes for W simultaneous writers.
- **Provider recommendations for GitHub remotes:** about 6 pushes and 15 read operations per second per repository. The instance has one outbound IP, so per-IP throttling by a remote is possible (unverified).
- **Bound:** one Node event loop (shared-nothing second instances are separate deployments), NAS CPU for git and the O(issues) read, and the remote's own limits.

**Scenarios:**

1. Solo NAS, 1 user, 10 repositories: trivial.
2. 10 users x 10 repositories: about 300 MB, under 1 request/s; baseline design is sufficient.
3. 50 users x 50 repositories: about 7.5 GB; 100 active clones need adaptive polling, deduplication, possibly the snapshot cache, and quotas.
4. 200 users: edge of a low-end NAS; recommend a second independent instance per team (or snapshot cache, shared object store, a different account store).
5. One hot repository, 20 concurrent writers: push mutex plus bounded jittered retry, about 10-40 s worst case for the last writer.
6. Burst of automation writes: per-clone queue and a global git concurrency cap give back-pressure (429/503); there is no write-behind.
7. Huge repository with a tiny `.gitboard/`: clone cost is dominated by trees (GitHub's study of a 4 GB repository measured 1.2-5 minutes for shallow, full and blobless clones); use a shallow clone for such repositories or a dedicated Gitboard branch; GitHub advises against repeated shallow fetches.
8. NAS reboot or remote outage: startup resets clones to the remote; reads come from the clone labelled stale; writes fail fast; nothing acknowledged is lost.
