## Context

The local server already pushes SSE `change` events when files change, and the client ignores the payload and refetches (`client.ts subscribe`). Hosted needs the same for many browsers, several server instances, and authorised access only.

## Decision

1. **Server-Sent Events** over HTTPS (HTTP/2 preferred) for server-to-browser updates. Writes go through ordinary POSTs; no bidirectional channel is needed.
2. An event is a **revision hint**: `{repo, branch, commit, tree}` and nothing else (no issue data, no paths). It tells the client to refetch with `If-None-Match: <tree>`. Hints are idempotent, so at-most-once delivery is sufficient and no durable event log exists.
3. **Reconnection:** `retry:` hint plus an initial `ready` event carrying the current revision; a reconnecting client compares and refetches only if different. `Last-Event-ID` replay is not implemented.
4. **Authorisation:** checked at connect and re-checked on the authorisation TTL (ADR-79c71bc); the stream is closed on revocation. Because events contain no data, a missed re-check cannot leak content.
5. **Fan-out is in-process on the repository's owner node.** SSE connections are routed by repository key like all requests (ADR-375920a). A pub/sub bus is introduced only if SSE terminates elsewhere (OQ-11).
6. Keep-alive comments every 25 s (existing behaviour) and per-user/per-repo connection limits.
7. The `GitboardClient.subscribe` contract gains an optional revision argument; the local client ignores it.

## Alternatives considered

- **WebSockets:** bidirectional, but nothing here needs it; needs sticky sessions and custom reconnect/auth framing; no benefit for hints. Reserve for presence/typing features if ever required.
- **Polling:** simplest and robust but multiplies load by users and gives worse latency; kept as a degraded fallback and as the client's behaviour when SSE is blocked.
- **Durable event stream with replay (Kafka/Redis streams):** infrastructure for a problem hints do not have.
- **Push of changed data over SSE:** creates a second data path and an authorisation surface.

## Rationale

Hints decouple delivery guarantees from correctness: any loss is repaired by the next fetch, and the data path stays the audited, authorised read path.

## Consequences

- Each connected browser holds one open connection on a node; limits per node apply (file descriptors, memory per connection about tens of KB [A]).
- Proxies and load balancers must allow long-lived responses and `X-Accel-Buffering: no` (already set locally).

## Scalability implications

Connections scale with active users and are sharded with their repositories. At 10,000 concurrent users, 10,000 open connections are an ordinary load for one Node process per few thousand connections [E]; the constraint is fan-out per hot repository (one event to many subscribers), which is O(subscribers) in memory and trivial in bytes.

## Open questions

- OQ-11 event distribution when API and engine separate; per-user connection caps.


## Amendment 2026-11-21 (self-hosted direction)

Still applies: SSE with idempotent hints. Fan-out is in-process in the single `gitboard serve` process (no owner-node routing, no pub/sub bus); events are produced by ADR-fe71de9 and may reuse the existing filesystem watcher. Authorisation is the session; streams close when the session or the user's access to the repository ends.
