## Context

The local server pushes server-sent events when files change, and the web client ignores the payload and refetches. The hosted app needs the same for several users, authorised, from one server process.

## Decision

1. **Server-Sent Events** over HTTPS carry updates from server to browser. Writes use ordinary POSTs; nothing needs a bidirectional channel.
2. An event is a **hint** that the board changed (repository and board branch, optionally the new commit); it carries no issue data. The client refetches through the normal, authorised read path. Hints are idempotent, so no event log or replay exists.
3. **Reconnection:** the stream starts with a `ready` event; a reconnecting client refetches if its revision differs. Keep-alive comments every 25 s (existing behaviour); the reverse proxy must not buffer the stream.
4. **Authorisation:** the session; the stream closes when the session ends or the user loses access to the repository.
5. Fan-out is in-process, in the single `gitboard serve` process (ADR-819be48). Events are produced by the sync manager after a fast-forward (ADR-fe71de9); the existing filesystem watcher may emit them.
6. Per-user and per-repository connection limits apply.
7. `GitboardClient.subscribe` gains an optional revision argument; the local client ignores it.

## Alternatives considered

- **WebSockets:** bidirectional, but nothing here needs it; extra reconnect and authentication framing. Rejected.
- **Polling by the browser:** robust, but multiplies load and latency; kept only as the client's fallback when SSE is blocked.
- **A durable event stream with replay:** infrastructure for a problem hints do not have. Rejected.
- **Pushing changed data over SSE:** a second data path and authorisation surface. Rejected.
- **Owner-node routing or a pub/sub bus:** only needed with several processes. Rejected for the single-process design.

## Consequences

- Each connected browser holds an open connection to the server (file descriptors and a small amount of memory per connection).
- Proxies must allow long-lived responses.
