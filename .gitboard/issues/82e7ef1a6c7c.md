- **Date:** 2026-11-21
- **Related:** FEAT-8c2e32c, ADR-0495ea1, ADR-dc3a07e, ADR-3f39a2f, ADR-79c71bc

## Context

Changes arrive from outside GitBoard (CLI users, other Git clients, other tools). The local product detects them with a filesystem watcher (`watch.ts`).
Hosted GitBoard must detect remote changes, remain correct if notifications are delayed, lost, duplicated or reordered, and not do work for repositories nobody is using.
GitHub documents: 10 s delivery timeout; no automatic redelivery of failed deliveries; deliveries retained 3 days for manual/API redelivery; payload cap 25 MB; deliveries may arrive out of order.

## Decision

1. **Webhooks are hints, not data.** A verified `push` event becomes a *revision hint* `(repoKey, ref, after-oid)` with the touched-paths summary when available. Handlers are idempotent; correctness never depends on dedupe (`X-GitHub-Delivery` is used only to drop duplicates cheaply).
2. **Verification:** HMAC-SHA256 (`X-Hub-Signature-256`) with constant-time comparison before any parsing; reply quickly (2xx well within 10 s) and process asynchronously.
3. **Demand-driven fetch.** On a hint: if the repository is cold (no cache, no subscribers) record the latest known oid and stop. If the payload proves `.gitboard/` untouched (complete path list, not truncated) record the oid only. Otherwise run a **single-flight, coalescing incremental fetch** of the board branch.
4. **Freshness probes at read time** when the last verification is older than `T_fresh` or webhook health for the repo is unknown. The probe is a **refspec fetch of the single board ref** (protocol v2 sends `ref-prefix` for that ref only), not `git ls-remote <ref>`, which was observed to send no ref-prefix and to scale with the repository's total ref count [F, measured locally].
5. **Reconciler.** A low-rate loop over *hot* repositories (cache present and subscribers or recent activity) probes the branch tip; the interval backs off with idleness. Cold repositories are never reconciled; they are verified at cold start.
6. **Webhook health tracking** per installation (last delivery time, failed-delivery detection via the App's delivery log API where available) shortens probe intervals when deliveries appear to be lost.
7. **External change during an active write** is handled by the CAS push (rejection, fetch, re-execute); no special path.
8. **Provider outages:** fetches back off with jitter and honour `Retry-After`; the node serves stale-labelled reads from warm cache.
9. Installation and repository membership events (`installation`, `installation_repositories`) trigger access invalidation and cache deletion (ADR-79c71bc).

## Alternatives considered

- **Polling all repositories:** O(total repositories) provider traffic regardless of use. Rejected.
- **Fetch on every webhook for every repository:** active code repositories push constantly; most pushes do not touch `.gitboard/`. Rejected in favour of demand-driven.
- **Webhook as source of data (apply payload diffs):** payloads are truncated/ordered unreliably and would create a second state path. Rejected.
- **Trusting webhook delivery for correctness:** not allowed by the provider's own delivery semantics.
- **REST ETag conditional requests as the probe:** possible (304s do not count against the primary limit when authorised [F, GitHub docs]), but it puts the REST API on the sync path. Kept only as a reconciliation fallback.

## Rationale

Work proportional to *active* repositories keeps webhook volume from becoming load: a push to a repository nobody has open costs a signature check and a map update.

## Consequences

- Hot-repo staleness is bounded by webhook latency (typically seconds [A], Phase 0 spikes) and, if hooks fail, by the probe interval.
- Hint routing requires the ingress to know the owner node (rendezvous hash) or to forward by repo key.
- Webhook secret and App private key are high-value secrets (ADR-79c71bc).

## Scalability implications

Webhook ingress is stateless and scales horizontally; per-node work scales with hot repositories. Probe traffic is the main provider-facing cost and is capped per node (formula in FEAT-84505b0 (capacity model)).

## Open questions

- Probe intervals and caps; use of the App delivery log API for loss detection; behaviour for repositories without webhooks (self-hosted or misconfigured): probe-only mode.
