- **Question:** How do users log in to a self-hosted instance, and who administers it?
- **Why it matters:** The local server has no authentication; a server that edits repositories and uses stored credentials must not be exposed without it, and NAS users often already run single sign-on.
- **Options:** Local accounts only; local accounts plus trusted-header login behind a proxy (Authelia, Synology SSO); OIDC. Admin model: first user is admin, registration closed by default, admin-created or invited users, per-user quotas.
- **Recommendation:** Local accounts first (scrypt via `node:crypto`, no new dependency), trusted-header login next, OIDC later. First-run admin, closed registration, invites, quotas. `gitboard serve` refuses a non-loopback bind without authentication.
- **Related:** FEAT-8c2e32c, ADR-87400e0
- **Decision / date:** 2026-11-21. Login by forge OAuth through a generic OAuth2/OIDC core with provider adapters; the MVP has the GitHub adapter only (Gitea, GitLab, Forgejo later, see FEAT-43d54b1). Access is limited to named identities; unknown identities go to a capped, expiring pending queue; named identities live in `users.json` on the data volume, not in Git. Each user has a random opaque internal id; a login identity is (provider connection, immutable subject); identities are linked only explicitly (logged-in linking or admin command), never by email or name. All admin actions, including the first admin and recovery, are commands run inside the container; there is no admin web UI, no local password login and no break-glass account in the MVP. Recorded in ADR-87400e0.
