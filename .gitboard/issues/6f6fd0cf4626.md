> **Rejected 2026-11-21 (never accepted); replaced by ADR-0aa6b23.** Not rejected on technical merit: the requirements changed to a self-hosted, multi-user server for any Git remote (see FEAT-cd25599). This text is kept as the analysis of the provider-hosted (SaaS) variant; references to other ADRs in this text point to proposals of that variant.

- **Date:** 2026-11-21
- **Related:** FEAT-8c2e32c, ADR-7027c6a, ADR-7a20520, ADR-7955eb5, ADR-0495ea1, ADR-9eb2543, ADR-db6547a

## Context

The brief proposes ephemeral worktrees (or temporary clones) to prepare writes, then commit, rebase, push. GitBoard operations are text patches
to one to a handful of small files (`parse.ts applyChanges`, `store.ts saveChanges`), so a checked-out file tree is not needed to compute a write.

## Decision

1. A write builds its commit with **Git plumbing in the bare cache**, without a working tree or index: `hash-object -w` for new blobs, `mktree` for the changed trees (`.gitboard/issues`, `.gitboard`, root), `commit-tree -p <tip>` with trailers. Blob content is written exactly as core produced it (no filters, no eol conversion).
2. The commit is published with a **compare-and-swap push**: a plain push of `<commit>:refs/heads/<branch>` that Git rejects unless it is a fast-forward of the remote branch (optionally `--force-with-lease=<ref>:<tip>` is never needed because force is never used). Success is the remote's `ok` for the ref (ADR-7955eb5 durability).
3. One operation (including multi-file ones: rank rebalance, unlink children, column remap, `repo.init`) is **one commit**. Operations are run by core through `RepoTransaction` (ADR-9eb2543).
4. The commit author is the acting user, the committer is GitBoard; trailers `Gitboard-Op: <idempotency key>` and `Gitboard-Actor: <user id>`.
5. Hooks, filters and external helpers are disabled in the cache's generated config (ADR-79c71bc); plumbing commands do not invoke them anyway.

## Alternatives considered

- **Worktrees (shared object store):** isolate workspaces but add `.git/worktrees` state, lock/prune handling, branch checkout exclusivity, checkout I/O proportional to the sparse cone and the whole checkout-time attack surface. Parallel worktrees give no speed-up because preparation is microseconds and the serialisation point is the push (ADR-db6547a).
- **Independent temporary clones:** strongest isolation, but pays network and disk per write. A pool would only mask that cost.
- **Shared object store plus per-write index (`read-tree` into a temporary `GIT_INDEX_FILE`):** avoids a checkout but reads the entire repository tree into an index, O(repo size). Replaced by direct tree construction of just the three affected levels.
- **Provider Git-data/Contents API commits:** rejected as the primary path (ADR-b33c5a6); possible per-repo exception (FEAT-cf759ba).
- **Libgit2/JGit:** see ADR-b33c5a6.

## Rationale

Plumbing reproduces what the filesystem implementation does (replace bytes of a few files) with no side effects, and the CAS push gives
the atomicity and conflict detection Git already provides. Removing the checkout removes the largest class of untrusted-content risk.

## Consequences

- No clean/smudge, `core.autocrlf` or `.gitattributes` effects apply to hosted writes. The repository's `.gitboard/.gitattributes` (`* text eol=lf`) means local checkouts normalise to the same bytes; CRLF files are preserved byte-for-byte by `parse.ts`.
- Tree building is O(entries in `.gitboard/issues`) per write (43 bytes per entry [F, measured]): 430 KB of raw tree at 10k issues, 4.3 MB at 100k. The push itself is a thin pack of a few hundred bytes (272 B at 10k, 392 B at 100k [F, measured locally with git 2.54]) because the new tree is deltaed against the old one.
- Id uniqueness has no exclusive-create on the remote: after every rebase onto a new tip the existence check is repeated (the 48-bit id space makes a clash negligible; `validate` reports duplicates).
- Push rejections from policy (branch protection, push protection, signing rules) are surfaced as distinct errors (FEAT-0a956bc, FEAT-cf759ba).

## Scalability implications

Per-write CPU and memory are small and local; there is nothing to pool. The throughput ceiling per branch is the push rate (ADR-db6547a).

## Open questions
