> **Rejected 2026-11-21 (never accepted); replaced by ADR-0aa6b23.** Not rejected on technical merit: the requirements changed to a self-hosted, multi-user server for any Git remote (see FEAT-cd25599). This text is kept as the analysis of the provider-hosted (SaaS) variant; references to other ADRs in this text point to proposals of that variant.

- **Date:** 2026-11-21
- **Related:** FEAT-8c2e32c, ADR-b33c5a6, ADR-79c71bc, ADR-dc3a07e, ADR-6f6fd0c

## Context

The brief proposes ephemeral workspaces with shared Git object caching, sparse checkout and worktrees. Investigation shows: sparse checkout only
limits the working tree, not downloaded objects; the data GitBoard needs (`.gitboard/`) is small compared with most repositories; and no operation
needs a checked-out file, because core works on file *text* and `parse.ts` patches strings.

## Decision

1. Each cached repository is a **bare repository** on node-local disk, keyed by tenant-qualified repository identity. **No working tree, no checkout, no index files in the shared cache, ever.**
2. Initial population: `git init --bare` then a **blobless partial fetch of the board branch only** (`--filter=blob:none`, `fetch.recurseSubmodules=no`), followed by one batched fetch of the blobs under `.gitboard/`. Sparse checkout is not used. For repositories whose history makes the blobless clone too expensive, the cold start may use `--depth=1` **once**, and the cache is then re-created instead of being deepened or incrementally fetched while shallow (see Consequences). Which threshold applies is decided by Phase 0 spikes (FEAT-84505b0).
3. Updates are incremental **non-shallow** fetches of the board branch. Caches that grow beyond a size or fetch-count threshold are deleted and re-created rather than garbage-collected.
4. **The cache is disposable.** It never contains state that is not on the remote. Deleting it is always safe.
5. **Lifecycle:** per-repository lease table in memory (requests, writers and subscribers hold leases); idle expiry (default 30 minutes [A]); eviction by LRU when disk exceeds a high-water mark; single-flight cold start per repository; failed cold start leaves nothing behind.
6. Local git configuration is generated by GitBoard (never taken from the repository) with hooks, filters, fsmonitor, credential helpers and external protocols disabled (ADR-79c71bc).
7. Shared object stores between repositories (alternates) are **not** used across tenants.

## Alternatives considered

- **Ephemeral clone per request:** simplest, isolates well, but pays cold-start network cost on every request. Rejected.
- **One long-lived non-bare clone per repo with sparse checkout:** materialises content, needs a lock per repo, and keeps all the checkout-time attack surface. Rejected.
- **Worktrees from a shared bare repo:** share objects but add admin state (`.git/worktrees`), per-branch checkout exclusivity, locking and cleanup, and still check out files. Rejected: nothing needs files (ADR-6f6fd0c).
- **Shared alternates across repositories or tenants:** saves disk for forks, but turns a cache bug into cross-tenant data exposure and complicates deletion on revocation. Rejected.
- **Network filesystem for the cache:** removes node affinity but is slow and weak for Git locking.
- **Shallow-only (no filter):** downloads every blob of the tip, which is unbounded for large repositories; and incremental shallow fetches are costly on the server. Rejected.
- **Treeless (`tree:0`) as default:** cheaper first clone, but GitHub recommends against treeless clones for repeated fetching; kept as a spike candidate only.

## Rationale

The data needed per repository is the tip commit, the trees on the path to `.gitboard/`, and the blobs inside it. A bare, shallow, blobless
cache fetches little more than that, needs no checkout and cannot execute anything from the repository.

## Consequences

- Cold start cost depends on the size of the tip's tree objects (for blobless fetches all trees of the tip commit are sent), not on history length; very large trees are the risk (scenario 7).
- **GitHub documents that repeated shallow fetches are the worst case for the server** ("shallow fetches are the worst possible options", github.blog clone study, Dec 2020) and discourages treeless clones for fetching. Therefore the baseline does not rely on incremental shallow fetches, and `tree:0` is not the default. Large-history repositories are handled by re-creating a shallow cache, or best by the dedicated board branch (FEAT-0a956bc Option 3).
- Any later feature that needs file checkout (archive/download) needs a new ADR and a separate sandbox.

## Scalability implications

Disk per repository is tens of KB to a few MB (assumptions in FEAT-84505b0 (capacity model)); disk scales with *active* repositories, not total. Eviction makes disk a soft limit; cold-start rate then becomes the cost of undersizing.

## Open questions

- Blobless full-history vs one-shot shallow thresholds (Phase 0 spikes). Idle timeout value. Disk high-water policy.
