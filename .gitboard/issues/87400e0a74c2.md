## Context

The local server has no authentication and relies on loopback binding (ADR-b9d4018). Self-hosting for several users needs login, per-user Git credentials, and protection against credential theft, cross-user access and server-side request forgery. The registry ADR (ADR-9d88632) says Gitboard never stores credentials; hosted mode must.

## Decision

1. **Accounts:** local accounts (scrypt via `node:crypto`), first-run admin, registration closed by default, admin-created or invited users. Optional trusted-header or OIDC login for NAS single sign-on. Accounts live in a file in the data directory; no database is introduced.
2. **Sessions:** signed, HttpOnly, Secure (behind TLS), SameSite cookies; CSRF defence for cookie-authenticated POSTs; login rate limiting. `gitboard serve` **refuses a non-loopback bind without authentication**. The loopback Host/Origin checks stay for `start`; `serve` uses a configured public URL.
3. **Per-user Git credentials:** an app-generated ed25519 SSH key per user (public key shown to add at the remote) and/or an HTTPS token. Encrypted at rest (AES-256-GCM) with an instance master key supplied by environment variable or key file stored outside the data directory; decrypted only for one git call (in memory or on a 0600 tmpfs file); never in argv, logs, API responses or the profile repository. `runGit` receives them through its existing `extraEnv`.
4. **Repository authorisation = the user's own credential:** a user sees and operates on repositories listed in their profile, resolved from the session (never from request paths; `registeredOnly` principle), and their clones are fetched and pushed with their credential only.
5. **Remote URL policy in hosted mode:** `ssh://`, scp-style and `https://` only; local paths, `file://` and `ext::` rejected; an admin-configured `allowedRemoteHosts` list, with private addresses allowed only for listed hosts (SSRF; the NAS's own Gitea is on the LAN).
6. **Git hardening for every call:** `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, hooks disabled, `protocol.allow` restricted, `fetch.recurseSubmodules=no`, `transfer.fsckObjects=true`, timeouts, no credential helpers other than ours, instance-managed `known_hosts` with strict checking after trust-on-first-use.
7. **Trust model:** users are semi-trusted; the design is safe by default but promises no isolation against a hostile user of the same instance (SH-9).
8. **Removal:** deleting a user deletes sessions, credentials and clones.

## Alternatives considered

- **GitHub App / OAuth login only (earlier proposal):** ties the product to one provider and to an operator-run service.
- **No accounts, rely on the reverse proxy only:** fine for one user; cannot give each person their own repositories and credentials. Trusted-header login covers proxy-authenticated setups.
- **A shared instance credential for all users:** one Git identity for everyone and a wide blast radius; allowed only as an opt-in team mode (SH-11).
- **Storing credentials unencrypted on disk:** weaker; the master key adds little complexity.

## Rationale

Per-user credentials keep Git's own authorisation authoritative and attribute commits correctly; the other controls address the realistic threats for a NAS that may be internet-reachable.

## Consequences

- Credential handling is the highest-impact code in the product and needs review and tests (leak, SSRF and traversal cases).
- The master key becomes an operational secret (backup, rotation).
- SSH behaviour differs across NAS operating systems (spike S1).

## Scalability implications

Negligible CPU (scrypt only at login). A flat account file is adequate for tens to low hundreds of users; revisit past ~200.
