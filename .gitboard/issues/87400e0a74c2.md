## Context

The local server has no authentication and relies on loopback binding (ADR-b9d4018). A self-hosted server for several users needs login, per-user Git credentials, and protection against credential theft, cross-user access, injection and server-side request forgery. ADR-9d88632 says Gitboard never stores credentials; hosted mode must. Forge research (2026-11-21): a GitHub OAuth App's `repo` scope is full read and write on all of a user's repositories and cannot be read-only; a GitHub App can be limited to selected repositories with Contents read or write, its user token being the intersection of the app's and the user's access; GitHub App user tokens last 8 hours with single-use refresh tokens.

## Decision

**Login and identity**
1. Login is by forge OAuth through a generic OAuth2/OIDC core with provider adapters. The MVP has one adapter, GitHub, registered by each instance as its own **GitHub App**; organisation owners must install it. An adapter declares its endpoints, the stable subject, the Git credential format (for GitHub, `x-access-token` as the HTTPS username), refresh behaviour, whether its tokens are safe for Git (scoped, full-account, none) and an optional can-push lookup. Provider-specific code is limited to login, token refresh and permission lookup; the Git data path stays provider-agnostic.
2. Each user has a random opaque internal id (128 bits), never derived from a forge. A login identity is (provider connection id, immutable subject: the numeric id or OIDC `sub`, never the username). One identity belongs to exactly one user; a user may have several. Identities are linked only explicitly (while logged in, or by an admin command), never by matching email or name.
3. Login identities (who you are to the instance) and forge connections (Git access grants) are separate records. A connection belongs to a **workspace**; the MVP has one workspace per user, `default`, and the first login creates both. All per-user state is keyed by (user id, workspace id), the session carries the active workspace id, and repository ids in the API are workspace-scoped.
4. Access is limited to **named identities**. The admin adds a login name and the server stores the numeric id and the login. An unknown identity that logs in becomes a pending record (capped, for example 50, expiring after about 7 days; both numbers are proposals) that the admin approves or rejects.
5. Accounts are stored in `users.json` on the data volume, written atomically; OAuth tokens are in separate encrypted files; nothing is in Git.
6. **Administration is by commands run inside the container**, including the first admin and recovery. There is no admin web UI, no local passwords and no break-glass account.
7. Sessions are signed, HttpOnly, Secure, SameSite cookies with CSRF defence. User state is checked on each request so disabling takes effect immediately; existing sessions survive a forge outage. `gitboard serve` always requires login; loopback `gitboard start` is unchanged.

**Credentials and authorisation**
8. The Git credential is the OAuth token from the GitHub login. Tokens are encrypted at rest with a master key supplied as a secret file outside the data directory, decrypted only in memory for one git call, and passed per call (never in argv, logs, API responses or the profile). Refresh is serialised per user and connection and the new pair is stored; a revoked or expired grant shows the repository as needing reconnection.
9. Authorisation is the user's own credential: a user sees and operates on repositories in their profile, resolved from the session and never from request paths, and their clones are fetched and pushed only with their credential. Read-only access shows a read-only board.
10. Remote URL policy: `https://` only in the MVP; local paths, `file://` and `ext::` are rejected; an admin allow-list of remote hosts, with private addresses allowed only for listed hosts (the SSRF control).

**Injection and hardening**
11. Gitboard runs git with an argument array, never through a shell. No user-controlled value may enter `GIT_SSH_COMMAND`. URLs, hosts and branch names starting with `-` are rejected, branch names are validated with `git check-ref-format`, and `--` precedes user-supplied values. git receives an allow-listed environment; the master key is read from a file, never the environment. Clones use an empty template directory and a disabled hooks path, and no submodule command is ever run.
12. Every git call uses `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, restricted `protocol.allow`, `fetch.recurseSubmodules=no`, `transfer.fsckObjects=true`, timeouts, and no credential helper but ours. Symlinked `.gitboard` content is rejected by the existing confinement. Git stays patched (the image is rebuilt on security releases).

**Deployment requirements (Docker only, ADR-819be48)**
13. Non-root user, read-only root filesystem, only the data volume writable; no host mounts, no Docker socket, no added capabilities, never privileged; the data directory on its own volume or filesystem with a quota, and backed up (accounts, credentials, profiles; clones are rebuildable); memory, CPU and process limits; outbound network restricted to an allow-list of Git hosts; TLS at a reverse proxy; the master key as a secret file.
14. The operator documentation, written when this ships, opens with the risks: users supply repository URLs, so the server connects on their behalf; their credentials are stored on the operator's machine (a leaked master key exposes all of them); hostile repository content is processed by git on the host; a user can try to fill the disk; a misconfigured proxy exposes a server that edits repositories; Git patches arrive only when the image is updated; users are semi-trusted and no isolation between users of one instance is promised.
15. Quota defaults (assumptions to confirm in Phase 0): 2 GB disk per user; 50 repositories per user; a clone is aborted above 500 MB or 10 minutes; 2 concurrent git processes per instance; request body 1 MB; issue file 1 MB; 10,000 `.gitboard` entries per repository; login attempts limited per user and per address.
16. Deleting a user deletes their sessions, credentials and clones.

## Alternatives considered

- **A GitHub OAuth App with the `repo` scope:** full read and write on every repository, no read-only scope, organisation approval needed where access restrictions are on. Rejected in favour of a GitHub App.
- **Local accounts with passwords, or a break-glass admin account:** a password endpoint to attack and more code; recovery by a command in the container gives the same power. Rejected.
- **Open registration through the forge login:** anyone who can reach the instance and has a forge account could sign in, add repository URLs, use disk and make the server connect outward. Rejected for named identities.
- **Linking identities by email or username:** can be unverified, renamed or reused. Rejected (account-takeover class).
- **Per-repository credential binding for several accounts on one provider:** replaced by workspaces.
- **A shared instance credential for all users:** one Git identity and a wide blast radius. Rejected.
- **Storing credentials unencrypted, or authorising once at login:** rejected.
- **Deferred, not rejected (FEAT-43d54b1):** more adapters (FEAT-caff4fa), SSH keys, pasted tokens and a shared team credential (FEAT-ddd1855), OIDC and trusted-header login (FEAT-0253626), organisation allow-lists (FEAT-4a86c8c), an admin screen (FEAT-e2bbda5), workspaces beyond `default` (FEAT-fbb4fe8).

## Consequences

- Credential handling is the highest-impact code in the product and needs review and tests for leaks, SSRF and traversal.
- The master key is an operational secret (backup, rotation).
- Org owners must install the GitHub App for organisation repositories; some organisations will refuse.
- With no local passwords, losing access to the container host means losing admin recovery.
