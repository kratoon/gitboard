## Context

Settings have different owners. Project definitions, columns and views belong to the repository and are shared. A user's repository list, remotes, preferences and personal views belong to that user (today: `repos.json` in the user config directory and `localStorage` in the browser). A multi-user instance must show each user their own projects based on their own settings, and the owner wants those per-user settings versioned in Git.

## Decision

1. **Three owners of settings** (table in document 07 §3.5): repository (`.gitboard/config.yaml`, shared, versioned), user (**profile**), instance (config file/environment). Secrets are separate and never in Git.
2. A **profile** is one user's settings in a versioned file `profile.yaml` (`version`, `identity`, `default`, `preferences`, `repos` with remote URL, optional per-user board branch and visible projects, personal saved views). It never contains secrets or machine paths.
3. **Two backings, same schema:** a **Git-backed profile** in a repository the user controls (read and written through the same sync manager, so edits are commits), or an **instance-local profile** file. The user can start local and move to Git-backed later.
4. The profile generalises the registry of ADR-9d88632 (it lists remotes, not paths), so a later `gitboard profile` could let the local CLI use the same file.
5. Bootstrapping: the account records only the profile location; a malformed or unreachable profile falls back to the last good copy.
6. Personal saved views live in the profile; shared saved views, if built, live in `.gitboard/config.yaml` (informs FEAT-cd7b875).
7. A new optional `boardBranch` key in the repository config is the shared default; the profile can override it per user. Older CLIs ignore it (`RepoConfigSchema` is `passthrough`).

## Alternatives considered

- **Per-user settings only in the instance database/files:** simple, but lost with the instance and not editable or shareable; no portability between instances.
- **Everything in the repository config:** forces personal preferences onto the team and cannot express per-user remotes.
- **Per-user preferences in browser `localStorage` (today):** not shared across devices and not visible to the server.
- **Profile as part of the account store only:** no versioning, which was the request.

## Rationale

It follows the project's own rule (what describes the project's work travels with the repo; what describes a person or machine stays out) and extends it with a portable, versioned home for the personal part.

## Consequences

- A new file format to specify, version and validate (Zod schema, `validate`-style checks).
- The profile repository is another remote needing credentials and sync; its failure must not break board access.
- Some preferences need an instance-local fallback for users without a profile repository.

## Scalability implications

Profiles are tiny; one extra clone per user.
