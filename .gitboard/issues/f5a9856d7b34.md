- **Question:** How is `gitboard serve` packaged and which platforms and versions are supported?
- **Why it matters:** The point of the project is that anyone can host it, including on a NAS with unusual SSH and container environments.
- **Options:** npm package only; npm plus a multi-architecture container image; vendor notes for Synology and QNAP. Minimum Node and Git versions, checked at startup.
- **Recommendation:** Ship the container image next to the npm package, check the Git version at startup (keep Git patched), and document reverse proxy and NAS setups.
- **Related:** FEAT-8c2e32c, ADR-819be48
- **Decision / date:** 2026-11-21 (see the updates below) (partly decided 2026-11-21: a container is the only supported way to run `gitboard serve`, see ADR-87400e0; still open: image architectures, minimum Node and Git versions, NAS-specific notes).
  - **Update 2026-11-21 (owner), decided so far:** image architectures `linux/amd64` and `linux/arm64` (no 32-bit ARM); the image uses Node 22 while the npm package keeps `engines: >=20` for local use; the minimum Git version is the oldest version that passes the Phase 0 spikes (the sparse index needs 2.37 or newer), the image ships a current patched Git configured by Gitboard on every call (not by a system gitconfig), and the server refuses to start below the minimum; the image is rebuilt weekly and on Git security releases; no SSH client in the MVP image (SSH is deferred); non-root, read-only root filesystem, one `/data` volume, secrets as files, the existing `/api/health` as healthcheck; distribution through GitHub Container Registry with exact-version and `latest` tags, built with buildx in CI and published on release only, sharing the npm package's version. Reverse proxy and NAS compose examples are written into `docs/` when this ships.
  - **Decided 2026-11-21 (owner):** running `gitboard serve` on a network-reachable bind outside a container is unsupported: it warns loudly at startup and requires an explicit flag acknowledging that. A loopback bind outside a container needs neither the flag nor the warning, so local development stays easy. The image sets a marker (an environment variable) that the server uses to recognise a container.
