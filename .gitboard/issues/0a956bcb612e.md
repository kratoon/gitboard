- **Question:** Locally board state is per checked-out branch. Which branch does a server read and write, and what happens when direct pushes to it are not allowed?
- **Why it matters:** It decides whether writes work on the common team setup (protected default branch), the commit noise and CI cost on the code branch, and where users' data lives.
- **Options:** (1) Default branch, direct push. (2) Configurable `branch` in `.gitboard/config.yaml`, default as in (1), with a per-user override in the profile. (3) Dedicated orphan branch containing only `.gitboard/` (tiny history, fast clone of huge repositories, no CI interaction, but not versioned with the code). (4) PR mode: write to a short-lived branch and open a PR (works with protection; edits become proposals).
- **Recommendation:** Option 2 with a precise error naming the rejecting rule. Treat option 3 as a supported configuration, not a different architecture. Defer option 4 to the optional-features phase and define its durability semantics then.
- **Related:** FEAT-8c2e32c, ADR-0aa6b23, ADR-7955eb5
- **Decision / date:** 2026-11-21.
  - **Default:** the repository's default branch, pushed directly. Push mode is implicit; there is no `mode` key in the MVP. PR mode and automatic branch discovery are deferred (FEAT-eee6af6).
  - **Config:** a top-level `branch` key in `.gitboard/config.yaml` on the default branch points to a dedicated branch. Top-level because it is per repository, and "board" is ambiguous with the per-project boards. Unknown keys are preserved by older tools (`RepoConfigSchema` is `passthrough`). On the board branch itself `branch` must be absent or equal to that branch; `gitboard validate` warns otherwise.
  - **Resolution order:** the user's per-repository override in the profile, then the repository's `branch`, then the default branch. The UI shows the board branch and warns when the user's override differs from the repository's setting.
  - **Protected branches:** a rejected push names the rule and suggests a dedicated branch.
  - **Initialisation:** a repository where Gitboard is not set up on the resolved branch is shown as "not enabled". Enabling is an explicit user action, never automatic, and needs write access (read-only users see an explanation). The user chooses the branch (default branch, or a new dedicated branch) and the first project key, name and columns, as `gitboard init` does. On the default branch, init is a normal commit and push. A dedicated branch is created as an orphan branch holding only `.gitboard/` (pushed from a fresh repository, so the code tree is never touched); the `branch` pointer on the default branch is a separate, optional step that needs push access to it, otherwise the choice is stored as the user's override and teammates are told how to add the pointer through an ordinary pull request. Two users initialising at once are resolved by the retry, which finds `.gitboard/` present and treats init as already done. Recorded in ADR-0aa6b23.
