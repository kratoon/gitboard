> **Rejected 2026-11-21 (never accepted); replaced by ADR-819be48.** Not rejected on technical merit: the requirements changed to a self-hosted, multi-user server for any Git remote (see FEAT-cd25599). This text is kept as the analysis of the provider-hosted (SaaS) variant; references to other ADRs in this text point to proposals of that variant.

- **Date:** 2026-11-21
- **Basis:** Option A was rejected as the primary architecture by the project owner; the rest is a proposed decision.
- **Related:** FEAT-8c2e32c, ADR-7955eb5, ADR-0495ea1, ADR-79c71bc

## Context

Hosted GitBoard must read and write issue files in repositories it does not own. Two families of access exist: provider REST/GraphQL APIs
(contents, trees, blobs, commits) and the Git protocol (fetch, push) over HTTPS.

## Decision

1. **The primary data path (reading issues, writing issues, detecting changes) uses Git transport** against the remote, with the system `git` binary, over HTTPS with short-lived tokens.
2. **Provider APIs are auxiliary only**: user authentication, repository discovery, permission checks, installation management, webhook management. They are never required to read or write an issue.
3. The engine must not contain provider-specific data-path code. Provider-specific code is limited to authentication, permission checks, webhook parsing and credentials (ADR-79c71bc).
4. A per-repository **fallback to provider content APIs** is allowed only if a repository policy makes Git pushes impossible (FEAT-cf759ba); it is not part of the baseline design and needs its own record.

## Alternatives considered

- **Option A, direct provider API:** stateless and simple, but every board view costs requests per directory/file, and writes consume content-creation quota. Quotas are per user, installation or app and become the scaling limit (limits cited in FEAT-84505b0 (capacity model)). It also hard-codes one provider and has directory/listing truncation limits. Rejected as primary.
- **libgit2 / isomorphic-git / JGit in-process:** fewer processes, but partial-clone, protocol-v2 and push-option coverage lags the reference implementation, and ADR-9d88632 already chose system `git`. Revisit only if process spawn cost dominates (measure in the Phase 0 spikes).
- **SSH transport:** the local product uses SSH. Hosted uses HTTPS with installation/user tokens because deploy keys are per repository and not revocable per user.

## Rationale

Git transport is provider-independent, has no REST rate limit, transfers only objects the cache lacks, and reuses Git's own
concurrency primitive (ref update). It does **not** remove provider limits: the provider still throttles and polices Git traffic, and
these limits are accounted for explicitly in FEAT-84505b0 (capacity model) rather than assumed away.

## Consequences

- We own repository storage, synchronisation and cleanup (ADR-0495ea1, ADR-82e7ef1).
- Provider push policies (protection, push protection, signing) apply and must be surfaced as errors.
- Requires the `git` binary and a Linux host with local disk.

## Scalability implications

Removes per-request provider quota from the data path. Remaining provider-side constraints: Git transport throttling (not documented as a numeric quota), webhook delivery behaviour, REST quota for auxiliary calls (per user token for authorisation checks, so it scales with users, not with total load).

## Open questions

- Whether undocumented Git-transport throttling is reached under realistic burst load (Phase 0 spikes (FEAT-84505b0)).
