## Context

ADR-7027c6a confined filesystem access to `core/storage` and postponed a storage interface until hosting is planned. Today `store.ts` and `projects/config.ts` call
`repo-files.ts` functions with `Repo = { root }`; every operation rescans all issues (`snapshot()`); multi-file operations write sequentially. The CLI and the hosted API may
be implemented independently, but must share schemas, parsing, validation, serialisation and business rules (ADR-9b13ab6).

## Decision

1. Introduce two interfaces in core, replacing direct use of `repo-files.ts` by services:
   - **`RepoSnapshot`** (read): config text and hash, list of issue ids, read one issue, read all issues, and a `revision` descriptor (opaque to core; filesystem: none).
   - **`RepoTransaction`** (write): stage replace/create/delete of issue files and config with their expected hashes; `commit()` applies them as a unit. Filesystem implementation applies immediately and atomically per file exactly as today; Git implementation collects a change set for a single commit (ADR-6f6fd0c).
2. **Reads are lazy**: single-issue operations read one file plus what they need; board/backlog use the full snapshot. A parsed snapshot can be handed in by the caller so adapters can reuse it across requests (ADR-dc3a07e).
3. Core still imports no filesystem or Git module outside `core/storage`; the Git-object implementation lives in the hosted engine package, not in core.
4. **Re-execution contract:** an operation is a pure function of (snapshot, input, clock, ids) producing staged writes, so it can be re-run against a newer snapshot (ADR-db6547a). `runtime()` global state is replaced by passing clock and id source in the context for hosted use.
5. CLI behaviour, file bytes, error codes and the parity tests must not change.
6. The hosted HTTP adapter is a **third adapter** over the same operation registry; it adds tenancy, revision headers and idempotency, and never forks business rules. The CLI and the hosted API remain independently deployable.

## Alternatives considered

- **Separate hosted implementation of services:** duplicates the rules; drift guaranteed. Rejected.
- **Operate on an in-memory file map for all operations:** smallest interface, but loads everything on every call and hides write sets. Rejected.
- **Wrap the filesystem with a virtual filesystem (memfs) and keep `repo-files.ts`:** keeps core unchanged but reintroduces workspace materialisation and per-request cost. Rejected.
- **Do nothing until hosting is built:** the refactor is the riskiest change to existing code and should be done first, locally, under the existing parity tests.

## Rationale

The seam already exists as a module; making it an interface is the smallest change that gives atomic multi-file writes, lazy reads and re-execution, which both the hosted engine and (as a side benefit) the local CLI need.

## Consequences

- Phase 1 refactor touches `store.ts`, `config.ts`, `service.ts`, `validate.ts` and `operations.ts` handlers' repo parameter; no user-visible change.
- Multi-file operations become atomic on Git and remain sequential-non-atomic on the filesystem (documented difference).
- Amends ADR-7027c6a's "no storage interface until hosting is planned" (hosting is now planned).

## Scalability implications

Enables O(1)-file reads for single-issue operations and snapshot reuse; the Git engine's cost model (incremental tree diff) depends on it.
