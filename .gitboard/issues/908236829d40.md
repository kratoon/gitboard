## Context

Gitboard only offers a Kanban board. People also want to look at the same issues in other ways, starting with
a backlog (open work as an ordered list), and want to choose which views a repository or a project offers:
for example a decisions project may only need the list, while a delivery project wants both.

## Decision

**A view is a read-only presentation of one project's issues.** Views change no stored data and add no new
file format. Anything a view needs from the data (ordering, what counts as done, progress) is computed once in
core, exactly like the board (ADR-0002). Built-in views: `kanban` (shown as "Board") and `backlog`. Adding a
view later means adding its id, its label in the UI and, if needed, a core query. There is no schema migration.

**Which views are enabled is configuration, layered like columns (ADR-0011):**

- `views` in `.gitboard/config.json` is the repository setting and `projects[].views` overrides it for one
  project. Resolution: project, then repository, then the built-in default (all views). An override replaces the
  layer below; it never merges.
- The list order is the tab order and the first entry is the default view. Ids are unique and at least one view
  must be enabled.
- Ids this version does not know (from a newer Gitboard, or a typo) are ignored when resolving, so a config
  never breaks the board; `gitboard validate` reports them as `UNKNOWN_VIEW`.
- The user's current pick is a per-browser preference (local storage), limited to the enabled views. It is not
  stored in the repository.

**Operations and CLI** (each is a registered operation, per ADR-0002):

- `views.show`, `views.set`, `views.reset`: `gitboard views show|set|reset [--project KEY]`. For example
  `gitboard views set --views backlog,kanban --project ADR`.
- `backlog.get`: `gitboard backlog [--project KEY] [--all]`.
- Board data includes the project's resolved `views`, so the UI needs no extra request.

**The backlog view:**

- It is the project's **open work as a list grouped by status**, in column order, using the same cards, the
  same order (ADR-0006) and the same `issue.move` operation as the board. Switching views never reorders
  anything.
- The **last column** of the project's effective columns is "done". It is hidden unless `includeDone` (`--all`)
  is set, and a project with a single column hides nothing. Issues with an unknown status stay visible, and epics
  are not rows: they appear in the epic panel as on the board (ADR-0010).
- In the UI each row shows reference, title, epic, labels and checklist progress, with inline priority and status
  pickers. Sections collapse and have a quick-add field. Rows can be dragged to reorder or to another section.
  Search and filters are shared with the board. A "Views" dialog edits the configuration through the operations
  above.

## Alternatives considered

- **A separate `defaultView` field:** more configuration for no gain; the first entry of the list is the default.
- **A "backlog" status or column:** columns are already configurable (ADR-0011), and a fixed status would clash
  with them. The backlog is a view over the existing statuses instead.
- **A project-wide backlog order with its own rank field:** another field that merges poorly and duplicates
  ADR-0006. Not needed while the backlog is grouped by status.
- **Saving the selected view in `config.json`:** it is a personal preference and would create noisy diffs.
- **User-defined views (saved filters, grouping, columns):** more general, but a larger design. Deferred
  (OQ-018).

## Consequences

- Repositories that do nothing keep both views, and nothing in existing files changes.
- The board and the backlog cannot drift apart because they share one query and one move operation.
- Hiding the last column assumes it means "done". Projects whose last column is something else (for example
  `rejected` in the `ADR` project) can enable only the board, or use `--all` and "Show done" (OQ-016).
- New views need a UI label and renderer, and the compiler flags a missing label.
