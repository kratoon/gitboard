- **Question:** ADR-30abf7d fixes a flat issues directory. Is that acceptable at thousands of issues?
- **Why it matters:** GitHub's repository-limits page recommends at most 3,000 entries per directory. A tree entry costs 43 bytes (measured), so a flat tree is 430 KB at 10k and 4.3 MB at 100k issues; pushes stay tiny (measured thin packs of 272-392 bytes) because Git deltas the tree. Sharding changes the file format, breaks old CLIs and complicates merges.
- **Options:** Keep flat; shard by id prefix in a `version: 2` format with readers that accept both; per-project subdirectories.
- **Recommendation:** Keep flat for now and treat 3,000 issues per repository as the decision trigger. Design a reader-compatible v2 layout before general availability, since it is a format decision.
- **Related:** FEAT-8c2e32c, ADR-30abf7d
- **Decision / date:** 2026-11-21. Shard now: layout version 2, `issues/<first two hex characters of id>/<id>.md`; the layout follows the config `version`, readers accept both layouts with the sharded copy preferred, new repositories start at version 2, migration is explicit (`gitboard migrate`, never on read) and every CLI command in a version 1 repository warns that migration is available. Recorded in ADR-66f29ce; implementation in FEAT-6cb8a58.
- **Discussion 2026-11-21 (owner leans towards subdirectories named by the first characters of the id):**
  - Path stays a pure function of the immutable id (`issues/ab/<id>.md`), so moving an issue between projects, parents or statuses still never relocates the file; the principle of ADR-30abf7d (layout independent of mutable fields) is kept.
  - Helps: the provider's 3,000-entries-per-directory recommendation (2 hex characters is 256 directories, so about 390 per directory at 100k issues, uniform because ids are random) and keeps each tree object small. Does not help: merge behaviour (Git merges trees per entry), and nothing about the "only `.gitboard/` changes" rule.
  - Costs: a format change; old CLIs would see no issues in a sharded repository unless the config `version` is bumped (the schema accepts only `version: 1`, so an old CLI then fails loudly instead of silently showing nothing); 256 directory reads for a small repository instead of one; mixed flat and sharded layouts need a duplicate-id check (the existing `DUPLICATE_ID` validation already works by id).
  - Cheap insurance either way: make readers accept both layouts, and route path construction through one function, before any repository needs the sharded layout.
