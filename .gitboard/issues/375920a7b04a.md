## Context

The brief proposes separating stateless API instances, Git workers, repository cache/storage nodes, sync workers and real-time delivery. Each needs the same
state: the repository cache and the current revision of the branch.

## Decision

1. **One node type, sharded by repository.** A *repo node* contains the HTTP adapter, Git engine, repository cache, snapshot cache, writer queues, sync coordinator and SSE hub, for the repositories it owns. Nodes are added to scale.
2. **Routing by repository key** (`provider:repoId`) with **rendezvous (highest-random-weight) hashing** over the live node set, applied at the edge for requests, SSE connections and webhook hints. Adding or removing a node moves only that node's share of repositories.
3. **Affinity is a performance mechanism, not a correctness mechanism.** If two nodes act on one repository (rebalance, partition), the CAS push and fetch semantics keep Git correct; at worst duplicate fetches and a retried push occur.
4. **Node-local disk only** for caches (no shared network filesystem). Node loss loses only cache; recovery is cold start, protected by single-flight and a per-node cold-start concurrency cap.
5. **Module boundaries** inside the node (`engine`, `sync`, `hub`, `auth`) are explicit so that a later split is a deployment change. Candidate splits, each only on measured need: stateless API frontends in front of engines; a pub/sub bus for events (OQ-11); dedicated nodes for large tenants.
6. **No distributed coordination service** at launch: membership by the orchestrator's health checks and a static or discovery-fed node list at the edge; leases and queues are in memory.
7. Back-pressure and load shedding: per-node and per-tenant concurrency caps for fetch, push and parse; 429/503 with `Retry-After` before saturation.

## Alternatives considered

- **Full five-component split now:** more network hops and failure modes; cache nodes require network storage or remote object access; sync and SSE would need the engine's state anyway. Rejected as premature.
- **Stateless workers pulling from a queue (Redis/SQS) with shared cache storage:** conventional, but the shared cache defeats Git performance and isolation.
- **Consistent hashing with virtual nodes:** comparable; rendezvous is simpler and has no ring state.
- **Single big node:** simplest; valid for Phase 2; the sharding key and module boundaries make it a configuration of one node.
- **Kubernetes-first:** orchestrator choice is orthogonal; nothing here requires it.

## Rationale

Cache locality dominates Git cost; the cheapest way to get it is to send each repository's traffic to the same place. Everything stateful then
lives in one process, so no distributed protocol is needed.

## Consequences

- Hot repositories cannot be spread over nodes; a single repository's reads and writes are bounded by one node (scenario 5; reads of a hot repo are served from memory so this is rarely the limit).
- Rebalancing causes cold starts; mitigated by drain (stop accepting new owners, finish leases) and gradual rehash.
- Edge must know node health quickly; stale routing is tolerated (point 3).

## Scalability implications

Capacity is additive in nodes for any workload spread over many repositories (users, repositories, storage, memory, CPU). Non-additive: a single repository's push rate, a single node's disk-bound cold-start rate after loss, and provider-side limits per installation or per repository. See scenarios in the scalability document.

## Open questions

- Membership/discovery mechanism; drain choreography; when to split API from engine; node sizing.
