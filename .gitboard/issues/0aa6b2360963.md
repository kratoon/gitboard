## Context

Clones and working trees are acceptable. The existing core already edits files in a working tree with minimal patches and hash-based preconditions, and ADR-7027c6a anticipated an opt-in commit. The server must add commit, fetch, push and conflict handling around it, per user. A local experiment (git 2.54, a synthetic repository of 3,200 code files, 200 issues, 41 commits) showed that a treeless clone with a sparse index of `.gitboard/` downloads no blob outside `.gitboard/`, still fetches the complete tip tree set, and then grows by only the changed trees and blobs per upstream commit; it was tested over `file://` only and is verified against real remotes in Phase 0 (FEAT-84505b0).

## Decision

**Clones**
1. One independent managed clone per (user, repository), under the instance data directory. The clone path is computed from the user id, the workspace id and the canonical remote URL; it is never stored.
2. Cloning is treeless (`--filter=tree:0`), `--no-checkout`, then a cone sparse checkout of `.gitboard/` in sparse-index mode, with an empty template directory and hooks disabled; blobless (`--filter=blob:none`) is the fallback for a remote that handles `tree:0` badly. Only the Gitboard branch is fetched, so on a dedicated Gitboard branch `.git` holds nothing but `.gitboard/` and its commits.
3. The server owns the clone: its working tree is clean between operations and is never edited by hand. On startup every clone is reset to its remote branch (nothing unacknowledged is worth keeping).
4. Git identity and credentials are passed per call (environment or `-c`), never written to a clone's `.git/config`, and no code assumes `.git` is a directory, so a shared object store can be adopted later (FEAT-a67602a).

**Gitboard branch**
5. The Gitboard branch is the repository's default branch, pushed directly. A top-level `branch` key in `.gitboard/config.yaml` on the default branch selects a dedicated branch (top-level because it is per repository; "board" is ambiguous with the per-project boards, hence the name "Gitboard branch"). Resolution order: the user's per-repository override in the profile, then the repository's `branch`, then the default branch.
6. The hosted app reads and writes only the resolved Gitboard branch; `.gitboard/` on any other branch is never read or merged into the view. Status lagging behind feature branches until a pull request merges is accepted. On the Gitboard branch itself `branch` must be absent or equal to that branch, and `gitboard validate` warns otherwise. There is no `mode` key and no automatic branch discovery.
7. A repository without `.gitboard/` on the resolved branch is shown as "not enabled". Enabling is an explicit user action and needs write access: the user picks the branch (the default branch, or a new dedicated one) and the first project key, name and columns, and the existing `repo.init` operation runs through the normal flow. A dedicated branch is created as an orphan branch holding only `.gitboard/`, built in a fresh repository and pushed as a new branch. The `branch` pointer on the default branch is a separate, optional step that needs push access; otherwise the choice is stored as the user's override. Concurrent initialisation is resolved by the retry (the second writer finds `.gitboard/` and treats init as done). Which choice the dialog preselects is decided in FEAT-1d615b2.

**Operations**
8. Under a per-clone write lock: fetch if stale, fast-forward to the remote branch, run the existing operation through `executeOperation`, commit, push fast-forward only with the user's credential, and acknowledge only after the remote accepts.
9. If the operation or its precondition fails, restore the working tree. If the push is rejected as non-fast-forward, reset to the remote branch, fetch, and re-execute the operation on the new tip (bounded attempts with jitter): minimal-patch writes merge edits to different fields and `expectedHash` turns same-field races into `CONFLICT`. A rejection by policy (protected branch, authentication) resets and shows the remote's message; a rejection for a signature or ruleset reason marks the repository read-only for that user (cached) with the message shown. Force-push is never used.
10. An in-process push mutex per (remote, branch) removes contention between users of the instance; correctness never depends on it.
11. **Only `.gitboard/` is ever changed.** Staging uses an explicit `.gitboard` pathspec, and before the commit and again before the push every changed path is verified to be under `.gitboard/`; otherwise the clone is reset and the operation fails. This holds for every commit the app makes, including initialisation and the orphan branch.
12. One commit per operation, no squashing; a team that finds it too noisy moves the board to a dedicated branch. Message `chore(board): <operation> <ref>`, trailers `Gitboard-Op` (idempotency key, so a retried request is recognised in recent history) and `Gitboard-Actor`; the author is the acting user. An opt-in skip-CI marker, off by default, is a string appended to the subject through a top-level `commitSuffix` key in the repository config (for example `commitSuffix: "[skip ci]"`), overridable per user and per repository in the profile (profile, then repository config, then none) and shown as a commented-out example in the `init` template. Message format and key name are proposals.
13. Reads use the existing filesystem reads under a read lock (ADR-dc3a07e).
14. The sync code lives in core as `core/git/sync.ts` (using only `runGit`), which also allows an opt-in `gitboard sync` for CLI users.

## Alternatives considered

- **A shared object store per remote with per-user worktrees:** saves disk and fetches, but one user's credential then populates objects another user's worktree can read, needing access proofs and per-remote locking. Deferred until measurements justify it (FEAT-a67602a, which records the rules).
- **One shared clone with a service credential:** every user acts as one Git identity and the instance credential becomes the authorisation boundary. Rejected.
- **Plumbing commits in bare repositories, no working tree:** needs a new commit builder and gives up the reuse of existing code. Rejected (ADR-6f6fd0c).
- **Write-behind (commit locally, push later):** violates the durability rule (ADR-7955eb5). Rejected.
- **Blobless as the default clone:** keeps all historical trees (504 of them against 304 in the experiment). Kept as the fallback only.
- **A full clone or a non-sparse checkout:** downloads every blob. Rejected.
- **A dedicated Gitboard branch by default for new repositories, or discovered by naming convention:** changes how the local agent flow works and needs the local worktree redirect first (FEAT-1d615b2). Deferred.
- **PR mode:** edits as proposals, with its own design questions. Deferred (FEAT-eee6af6).
- **Squashing bursts into one commit; a skip-CI marker on by default:** loses attribution; surprises users by changing their CI. Rejected.

## Consequences

- Disk grows with users, repositories and workspaces (a few MB per clone is typical; large repositories dominate through their tree objects).
- Each write costs a push round trip.
- Sparse checkout limits, but does not remove, checkout-time attack surface; Git must be kept patched (ADR-87400e0).
- The local CLI refuses writes on a branch whose config points elsewhere (FEAT-54f054d); using a dedicated Gitboard branch locally needs a worktree until FEAT-1d615b2.
