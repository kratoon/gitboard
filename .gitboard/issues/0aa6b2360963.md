## Context

Clones and working trees are now acceptable. The existing core already edits files in a working tree with minimal patches and hash-based preconditions, and ADR-7027c6a anticipated an opt-in `commit`. The server must add commit, fetch, push and conflict handling around it, per user.

## Decision

1. **One managed clone per (user, repository)** under the instance data directory: `--filter=blob:none`, `--no-checkout`, then cone sparse-checkout of `.gitboard/`, with hooks disabled. The server owns the clone; its working tree is clean between operations and is never edited by hand.
2. **Operation flow, under a per-clone write lock:** fetch if stale, fast-forward to the remote branch, run the existing operation through `executeOperation`, commit only `.gitboard/` (author = the acting user, trailer `Gitboard-Op: <idempotency key>`), push fast-forward only with the user's credential, acknowledge **only after the remote accepts**.
3. **Failure handling:** if the operation or its precondition fails, restore the working tree. If the push is rejected as non-fast-forward, reset to the remote branch, fetch, and **re-execute the operation** on the new tip (bounded attempts with jitter): minimal-patch writes merge edits to different fields, `expectedHash` turns same-field races into `CONFLICT`. Policy rejections (protected branch, auth) reset and surface the remote's message. Never force-push.
4. **In-process push mutex per (remote, branch)** removes contention between users of the same instance; correctness never depends on it.
5. **Reads** use the existing filesystem reads under a read lock. An optional tree-keyed snapshot cache (ADR-dc3a07e) is the later optimisation.
6. **Startup recovery:** reset every clone to its remote branch (nothing unacknowledged is ever worth keeping).
7. **Idempotency:** trailers allow a retried request to be recognised in recent history after a lost reply.
8. Worktrees are **not required**. An optional shared object store with per-user worktrees (S3) is allowed later if disk or network duplication is measured to matter; temporary worktrees are the tool for a future PR mode.
9. The sync code lives in core as `core/git/sync.ts` (using only `runGit`) so the CLI can offer an opt-in `gitboard sync`, as ADR-7027c6a anticipated.

## Alternatives considered

- **Shared bare mirror per remote with per-user worktrees (S3) now:** saves disk, but one user's credential populates objects another user's worktree can read, needing access proofs and per-remote locking. Deferred until measurements justify it.
- **Single shared clone with a service credential:** simplest, but all users act as one Git identity and the instance credential becomes the authorisation boundary. Allowed only as an opt-in team mode (SH-11).
- **Plumbing commits in bare repositories (earlier proposal):** no longer needed once checkouts are acceptable; reuses less existing code.
- **Write-behind (commit locally, push later):** violates the durability rule.

## Rationale

It reuses the core unchanged and gives each user their own Git identity, credential boundary and history attribution, at the price of some duplication that blobless + sparse clones keep small.

## Consequences

- Disk grows with users x repositories (typically a few MB each; large repositories dominate).
- Each write costs a push round trip (about 0.5-2 s [A]).
- Sparse checkout limits, but does not remove, checkout-time attack surface; Git must be kept patched.

## Scalability implications

Per-instance, serial per clone; contention is negligible at the target scale. See document 07 §7 for formulas and scenarios.
