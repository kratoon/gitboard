## Context

Clones and working trees are now acceptable. The existing core already edits files in a working tree with minimal patches and hash-based preconditions, and ADR-7027c6a anticipated an opt-in `commit`. The server must add commit, fetch, push and conflict handling around it, per user.

## Decision

1. **One managed clone per (user, repository)** under the instance data directory: `--filter=tree:0`, `--no-checkout`, then a cone sparse checkout of `.gitboard/` in sparse-index mode, with hooks disabled (blobless, `--filter=blob:none`, is the fallback for remotes that handle `tree:0` badly). The server owns the clone; its working tree is clean between operations and is never edited by hand.
2. **Operation flow, under a per-clone write lock:** fetch if stale, fast-forward to the remote branch, run the existing operation through `executeOperation`, commit only `.gitboard/` (author = the acting user, trailer `Gitboard-Op: <idempotency key>`), push fast-forward only with the user's credential, acknowledge **only after the remote accepts**.
3. **Failure handling:** if the operation or its precondition fails, restore the working tree. If the push is rejected as non-fast-forward, reset to the remote branch, fetch, and **re-execute the operation** on the new tip (bounded attempts with jitter): minimal-patch writes merge edits to different fields, `expectedHash` turns same-field races into `CONFLICT`. Policy rejections (protected branch, auth) reset and surface the remote's message. Never force-push.
4. **In-process push mutex per (remote, branch)** removes contention between users of the same instance; correctness never depends on it.
5. **Reads** use the existing filesystem reads under a read lock. An optional tree-keyed snapshot cache (ADR-dc3a07e) is the later optimisation.
6. **Startup recovery:** reset every clone to its remote branch (nothing unacknowledged is ever worth keeping).
7. **Idempotency:** trailers allow a retried request to be recognised in recent history after a lost reply.
8. Worktrees are **not required**. An optional shared object store with per-user worktrees is allowed later if disk or network duplication is measured to matter; temporary worktrees are the tool for a future PR mode.
9. The sync code lives in core as `core/git/sync.ts` (using only `runGit`) so the CLI can offer an opt-in `gitboard sync`, as ADR-7027c6a anticipated.

## Alternatives considered

- **Shared bare mirror per remote with per-user worktrees, now:** saves disk, but one user's credential populates objects another user's worktree can read, needing access proofs and per-remote locking. Deferred until measurements justify it.
- **Single shared clone with a service credential:** simplest, but all users act as one Git identity and the instance credential becomes the authorisation boundary. Allowed only as an opt-in team mode (FEAT-94dfdce).
- **Plumbing commits in bare repositories (earlier proposal):** no longer needed once checkouts are acceptable; reuses less existing code.
- **Write-behind (commit locally, push later):** violates the durability rule.

## Rationale

It reuses the core unchanged and gives each user their own Git identity, credential boundary and history attribution, at the price of some duplication that blobless + sparse clones keep small.

## Consequences

- Disk grows with users x repositories (typically a few MB each; large repositories dominate).
- Each write costs a push round trip (about 0.5-2 s [A]).
- Sparse checkout limits, but does not remove, checkout-time attack surface; Git must be kept patched.

## Scalability implications

Per-instance, serial per clone; contention is negligible at the target scale. See the Resource model section below.

## Decision update 2026-11-21 (owner)

Option 1 confirmed: independent clone per (user, repository), blobless, cone sparse checkout of `.gitboard/`. The shared object store with per-user worktrees remains the planned upgrade if measurements justify it (FEAT-02f3376). Constraints that keep that upgrade cheap:

1. All clone creation, sync and path lookup live in one module; nothing else builds clone paths.
2. Clone paths are never stored; they are computed from the user and the canonical remote URL.
3. A canonical-URL function exists from the start (also used to deduplicate polling per remote).
4. Git identity and credentials are passed per call (environment or `-c`), never written into a clone's `.git/config`.
5. No code assumes `.git` is a directory (it is a file in a worktree).

## Clone contents (owner decision 2026-11-21; local experiment, git 2.54, synthetic repository)

Goal: keep `.git` as small as Git allows. Measured on a repository with 3,200 code files in 300 directories, 200 issues and 41 commits:

| Clone | Blobs | Commits | Trees | Working-tree files |
|---|---|---|---|---|
| Full | 3,280 | 41 | 504 | 3,200 |
| Blobless + sparse | 200 | 41 | 504 (all historical) | 200 |
| Treeless + cone sparse, sparse index | 200 | 41 | 304 (tip tree set only) | 200 |
| Ideal (only `.gitboard`) | 200 | 41 | 3 | 200 |

- No blob outside `.gitboard/` is ever downloaded.
- Git still fetches the complete tip tree set even to read one path (`rev-parse HEAD:.gitboard` alone fetched all 304). Trees are small (43 bytes per file entry, measured; an estimate of about 5 MB at 100k files and 50 MB at 1M files), so this only matters for huge repositories. A dedicated board branch is the only way to have literally nothing else (FEAT-0a956bc).
- Updates stay small: each upstream commit added about 5-7 trees plus the changed `.gitboard` blobs, not the whole tree set again.
- A commit in the sparse-index clone touched only `.gitboard`, `git status` was clean and nothing else was deleted.
- Tested over `file://` only. GitHub and Gitea behaviour with `tree:0` (GitHub advises against treeless clones for repeated fetches, a warning about the submodule check, which is disabled with `fetch.recurseSubmodules=no`) is verified in Phase 0 (FEAT-84505b0).

Constraint 2 above is refined: the clone path is computed from the user id, the workspace id and the canonical remote URL (the MVP has one workspace, `default`).

## Decision update 2026-11-21 (owner): board branch and initialisation

- The board branch defaults to the repository's default branch, pushed directly. A top-level `branch` key in `.gitboard/config.yaml` on the default branch selects a dedicated branch. Resolution order: the user's per-repository override in the profile, the repository's `branch`, the default branch. There is no `mode` key and no automatic discovery in the MVP (FEAT-0a956bc, FEAT-eee6af6).
- **Clone shape follows the branch.** The clone fetches only the board branch. On a dedicated branch, `.git` therefore holds nothing but `.gitboard/` objects and its commits.
- **Initialisation by the hosted app:** a repository without `.gitboard/` on the resolved branch is "not enabled". On explicit user action with write access, the existing `repo.init` operation (project key, name and columns) runs through the normal flow: operation, commit, push. For a dedicated branch an orphan branch containing only `.gitboard/` is created in a fresh repository and pushed as a new branch. The `branch` pointer commit to the default branch is optional and may be rejected by protection; the user's override stored in the profile still works.
- `repo.init` currently also registers the repository in the local registry; in hosted mode registration and initialisation are separate steps.
- Concurrent initialisation is resolved by the retry: the second writer finds `.gitboard/` and treats init as already done (it is idempotent today).

Source of truth (owner, 2026-11-21): the hosted app reads and writes only the resolved board branch. Issue files on any other branch are ignored. Status lagging behind feature branches until merge is accepted. See FEAT-0a956bc; the local-CLI side of dedicated branches is deferred in FEAT-1d615b2.

Commits (owner, 2026-11-21): one commit per operation, no squashing; excessive noise is resolved by moving the board to a dedicated branch. A skip-CI marker is **on by default**: the text `[skip ci]` is appended to the commit subject (`chore(board): <operation> <ref> [skip ci]`). It is configurable and can be turned off per repository in the repository config, and overridden per user (and per repository) in the profile; resolution order profile, repository config, default. Proposed shape: one top-level key `commitSuffix` (a string; default `[skip ci]`; an empty string or `false` turns it off; another string suits another CI system). Key name is a proposal. GitHub documents `[skip ci]`, `[ci skip]`, `[no ci]`, `[skip actions]` and `[actions skip]` for `push` and `pull_request` workflows, and warns that workflows skipped by a commit message leave their checks "Pending", which blocks a pull request that requires them: the reason for the off switch. A `skip-checks: true` trailer also works but must be the last trailer, so the subject suffix is used. Path filters in the CI configuration remain an alternative. FEAT-87eea79.
