## Context

Many users may write to one repository at once. Git serialises ref updates: of N simultaneous pushes to a branch from the same tip only one is accepted.
GitHub documents recommended maximums of **6 pushes per minute per repository** and 15 read operations per second per repository
(repository-limits page). These are recommendations, not enforced quotas, but exceeding them risks throttling.

## Decision

1. **One writer per `(repo, branch)`** at a time, enforced by an in-process queue on the node that owns the repository. Correctness does not depend on this: the CAS push is the real arbiter; the queue only removes contention.
2. **Write coalescing (group commit).** While a push is in flight, arriving operations queue. The next cycle takes *all* queued operations, applies them sequentially to the same tip (one commit each, preserving attribution), and pushes once. An idle branch pushes immediately (latency of one push for a lone write).
3. **Push-rate governor** per repository, default aligned with the documented recommendation (about 6 pushes/min averaged, small burst allowed [A]); under sustained load operations wait for the next cycle, so latency rises instead of push rate.
4. **Semantic retry.** On non-fast-forward rejection: fetch, then **re-execute each operation** against the new tip (all invariants re-checked: parent exists, status valid in the current config, id unused) and push again. Bounded attempts with jittered backoff; then `RETRY_LATER`/503. Never force-push, never textual-rebase.
5. **Conflict policy.** Operations carrying `expectedHash` fail with `CONFLICT` if the file content differs at execution time. Operations without a precondition apply as minimal key patches, so edits to different fields of one issue merge; the same field edited concurrently is last-writer-wins and this is stated API behaviour. User-edit paths in the UI send `expectedHash` already; the hosted API should require it for body/title edits.
6. **Commit granularity under load.** Up to 20 operations per batch are committed one commit each (attribution, per-op trailers). A larger batch is squashed into one commit carrying every `Gitboard-Op` trailer and `Co-authored-by` lines, so sustained high write rates do not grow history without bound (see Consequences).
7. **Failure isolation inside a batch.** An operation that fails validation or its precondition is rejected alone. If the remote rejects the push for a non-retryable policy reason, the batch is split (bisected) to find the offending commit.
8. **Idempotency.** Writes carry an `Idempotency-Key`, stored as a `Gitboard-Op` trailer. Before executing, the writer searches recent history of the board branch for the key and returns the stored outcome if found; this also resolves the "pushed but reply lost" case without any database.
9. **Unknown outcome.** If the push result is unknown (timeout), fetch and test whether the commit is reachable from the remote tip before answering or retrying.

## Alternatives considered

- **Parallel workspaces with parallel pushes:** with W simultaneous writers and naive retry, total push attempts are W(W+1)/2 (5,050 for W=100) and most fail; incompatible with the 6/min recommendation. Rejected.
- **Distributed lock (Redis, database) per branch:** adds infrastructure for something affinity routing gives for free; does not replace the CAS anyway.
- **Textual rebase/merge on conflict:** can conflict on adjacent frontmatter lines and produces results no operation intended. Rejected in favour of re-execution.
- **One squashed commit per batch:** fewer commits but loses per-user attribution and idempotency trailers. Left as an option (OQ-6).
- **Optimistic acknowledgement before push:** violates durability (ADR-7955eb5).

## Rationale

Because preparation is cheap and the push is the bottleneck, the only lever is *fewer pushes for more writes*. Group commit converts a hot branch from
a throughput problem into a latency one, and re-execution exploits the minimal-patch property the CLI already has.

## Consequences

- Latency of a write under sustained load is up to one push-governor interval plus a push (order of 10 s at 6/min [E]); a lone write is one push round trip (about 0.3-1 s [A]).
- Ops per second per branch is effectively unbounded by Git (bounded by batch size and CPU) but latency is not.
- Same-field concurrent edits without preconditions silently lose the earlier value (documented).
- **History growth is the real long-run limit of a hot branch.** Each commit adds roughly 0.4-1 KB of pack data [E, from measured thin packs plus commit object]. At a sustained 1 write/s that is about 86k commits/day, 35-85 MB/day, exceeding GitHub's recommended 5-10 GB repository size within months. Squashing large batches and the dedicated board branch (OQ-1) are the mitigations; per-op commits are fine for ordinary rates.

## Scalability implications

Contention cost is O(batches), not O(writers^2). The ceiling for one repo is governed by the push governor and provider tolerance, not by node capacity; other repositories are unaffected (scenario 5).

## Open questions

- Governor defaults; batch size cap; whether a repository-level "write burst" mode may exceed 6 pushes/min when the provider tolerates it (spike S3).
