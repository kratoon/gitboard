- **Question:** Should an issue also open on its own full page, with its own URL, instead of only in the side
  panel? Should the drawer get an "Open full page" action, and should that URL be a deep link that opens the
  issue directly on load?
- **Things to weigh:**
  - It needs a route per issue, for example `/repos/<repo id>/issues/<ref>`. The server already serves the app
    for unknown paths, so no server change is required.
  - The page would reuse the drawer's content (fields, checklist, description, delete) together with its
    conflict handling and live refresh, so there is one implementation, not two.
  - A link only works on the machine that registered the repository, because the repository id comes from the
    local registry. That matches the local-first scope (see the hosted / multi-user question).
  - The back and forward buttons and a reload should keep working on the issue page, and closing it should return
    to the board or backlog the user came from.
  - It pairs with copying a reference (FEAT-6930f51): a "copy link" could be added there once pages exist.
- **Recommendation:** Yes, after the copy button. Add the route, reuse the drawer's content as the page body,
  and add an "Open full page" button to the drawer. Neither needs a new core operation: both use `issue.get` and
  `issue.update` as today.
- **Decision / date:** 2026-11-21, partly decided; the rest is a proposal to confirm.
  - The issue stays in the side panel, and also opens on its own page. Issue keys (`KEY-shortid`) found in
    rendered text become links to that page. Only keys that resolve in the current repository are linked.
  - The URL identifies the repository by its **origin**, not by the machine-local registry id:
    `/repos/<owner>/<name>/issues/<ref>`, taken from the normalised `origin` URL (scheme, host, credentials
    and `.git` removed, lowercased). Local and cloned repositories of the same origin get the same path.
  - A provider (adapter) segment is added only when two registered repositories would otherwise share an
    `<owner>/<name>` across providers: `/repos/<provider>/<owner>/<name>/issues/<ref>`, for example
    `github` and `gitlab` for `github.com/acme/api` and `gitlab.com/acme/api`.
  - A repository with no origin must set a unique `id` in `.gitboard/config.yaml`, which is committed with the
    repository, so every clone has the same path.
  - The HTTP API keeps using the registry id; only the web routes use the origin path.
- **Proposed, to confirm:**
  - The URL always accepts the provider-qualified form; the unqualified form works when it is unambiguous.
    Generated links are qualified only on a conflict, so such a link may break on another machine that has
    no conflict, or the reverse.
  - Repositories with no origin and no configured `id` are not broken: their links use the registry id and
    the app tells the user to configure an `id`.
  - If `origin` is missing and the configured `id` exists, the configured `id` wins over a guessed name.
  - A configured `id` overrides the origin-derived path when both exist.
