- **Goal:** implement the layout decided in the layout v2 ADR, as a core change that is useful on its own and is a prerequisite of the hosted phases.
- **Includes:**
  - Layout follows the config `version`: 1 is flat (unchanged); 2 is `issues/<first two hex characters of id>/<id>.md`. All path construction goes through one function.
  - Readers accept both layouts in either version; when an id exists in both, the sharded copy wins and `gitboard validate` warns when the contents differ, and when flat files remain in a version 2 repository.
  - Writers never write the sharded layout in a version 1 repository. In a version 2 repository an update of a leftover flat issue writes the sharded path and removes the flat copy.
  - `gitboard init` creates version 2 repositories.
  - `gitboard migrate`: moves flat issues into shard directories and bumps `version` to 2; idempotent; stops and reports if the same id exists in both places with different content. It is its own operation, and changes only `.gitboard/`.
  - Every CLI command in a version 1 repository prints a warning recommending `gitboard migrate` (text mode on stderr; in `--json` mode in `warnings`, so agents see it too). The agent skill text mentions it.
  - Tests: parity across core, CLI and HTTP; fixtures for flat, sharded and mixed repositories; duplicates; idempotent migration; an old CLI failing loudly on `version: 2` (the schema accepts only `version: 1`).
  - When shipped, the README issue-format section and the skill are updated in the present tense.
- **Hosted side (Phase 2):** reads both layouts, writes in the repository's current version, and offers an explicit "upgrade layout" action to users with write access; never migrates on read.
